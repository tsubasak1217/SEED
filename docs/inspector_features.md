# インスペクタの編集支援機能 — 画像比率・ロック・スケール連動

インスペクタ（`editor/src/Panels/InspectorPanel*`）に載っている 3 つの編集支援機能の仕様と実装地図。
いずれも **値の反映は既存の経路（IPC / Undo）をそのまま通す**。
インスペクタ側は「送る前にフィールドの値を整える」だけで、独自の送信経路は持たない。

| 機能 | 何をする | 実装ファイル | 純粋ロジック |
|---|---|---|---|
| 画像比率に設定 | 元画像の縦横比で幅・高さの片方を計算し直す | `InspectorPanel.ImageAspect.cs` | `Panels/Inspector/ImageAspectCalculator.cs` |
| インスペクタのロック | 他のアクターを選んでも表示対象を切り替えない | `InspectorPanel.Lock.cs` | （UI 状態のみ） |
| スケール連動 | X/Y/Z の 1 つを編集すると他も同じ比率で変わる | `InspectorPanel.ScaleLink.cs` | `Panels/Inspector/ScaleLinkCalculator.cs` |

純粋ロジックは WPF に依存させず、`editor/tests/InspectorLogicTests` から直接検証している
（WPF 型を使い始めるとテストがビルドできなくなり、それが癒着の検知器になる）。

---

## 1. 画像比率に設定

### 1-1. 出る場所と条件

**SpriteComponent の「幅」「高さ」欄の直下**に「画像比率に設定 ▾」ボタンが出る。
**テクスチャが設定されているときだけ**出す（未設定なら比率の取りようがないので行ごと出さない。
`.claude/rules/editor-panels.md` の「選択に応じて無関係なパラメータは出さない」方針）。

メニューは 2 項目。

| 項目 | 動作 |
|---|---|
| 縦基準（高さを保ち幅を合わせる） | 高さはそのまま、幅 = 高さ × (画像幅 ÷ 画像高さ) |
| 横基準（幅を保ち高さを合わせる） | 幅はそのまま、高さ = 幅 ÷ (画像幅 ÷ 画像高さ) |

### 1-2. 対象コンポーネントの選定

`ComponentCatalog` と各スロット UI を突き合わせた結果、
**「画像参照 ＋ 自前の幅・高さ」を両方持つのは `SpriteComponent` だけ**。

- 3D スプライトも、キャンバス（2D アクター）上の画像も、実体は同じ `SpriteComponent`
  （`texture_path` ＋ `width` / `height`）。`CanvasTransform` はサイズを持たず**スケール（倍率）
  しか持たない**ので、「キャンバスの画像のサイズ」＝そのアクターに載っている Sprite の幅・高さ。
  したがって Sprite に付ければ 3D・2D の両方をカバーできる。
- `SkinnedSpriteComponent` は寸法をメッシュ（`.sprite_mesh`）が持つので対象外。
- `SkyboxComponent` / `ParticleEmitterComponent` は画像を参照するが、
  「元画像の縦横比で決めるべき幅・高さ」を持たない。
- `CanvasComponent` は幅・高さを持つが画像を参照しない。

対象を増やすときは `BuildImageAspectRow(...)` を呼ぶ行を足すだけでよい。

### 1-3. `auto_scale` との関係（重要）

**Sprite に `auto_scale` は存在しない。** `runtime/src/engine/components/sprite_component.rs` の
`SpriteComponent` のフィールドは `texture_path` / `color` / `width` / `height` / `layer` /
`postfx_path` / `raycast_target` のみ。

`auto_scale` は **`CanvasComponent`** のフラグで、
「ルートキャンバスをビューポート解像度へ自動追従させるか」を決めるもの（`canvas_collect.rs`）。
スプライトの幅・高さには関与しないため、本機能と競合しない
（「auto_scale が ON ならボタンを隠す」といった出し分けは不要）。

近い設定である `CanvasTransform` の `scale_size` / `keep_aspect_ratio` は
「親キャンバスの拡縮にどう追従するか」であり、ここで書き換える**基準サイズ**とは層が違う。
基準サイズを画像比率に揃えたうえで、表示時の追従は従来どおり効く。

### 1-4. 元画像の寸法の取り方

`Panels/Inspector/ImageSizeCache.cs` が `BitmapDecoder` に**ヘッダだけ**読ませる
（`DelayCreation` ＋ `BitmapCacheOption.None`、自前 `FileStream` を即閉じてファイルを掴まない）。

- 結果は**パス単位でキャッシュ**する。あわせて**最終更新日時とファイルサイズ**も覚え、
  画像を描き直して上書き保存したら読み直す。
- 失敗（未対応形式・破損・ファイル無し）も「失敗した」という結果としてキャッシュする。
- WPF のコーデックが無い形式（`.tga`、環境によっては `.webp`）は取得できない。
  その場合はボタンのツールチップに「元画像の寸法を読み取れませんでした」と出し、
  押しても値は変えずログに残すだけ（サイズを 0 にするような壊し方はしない）。

### 1-5. 計算規則（`ImageAspectCalculator`）

- 画像の幅・高さが 0 以下、保つ側の辺が 0、現在値が NaN / ∞ → **何も変えない**。
- **符号は維持する**。スプライトの幅・高さは反転表示に負値が使われることがあるので、
  比率は「保つ辺の絶対値」から求め、書き換える辺の符号は元の値の符号を引き継ぐ
  （元が 0 のときは正）。単純に比率を掛けると、保つ辺が負のとき書き換える辺まで反転してしまう。
- 書き換えるのは変化した側のフィールドだけ。表示桁数は元のフィールドの書式に合わせる。
- 確定は既存の `CommitSize()`（`SET_SPRITE_SIZE`）を 1 回呼ぶだけ。
  **IPC も Undo も従来のサイズ変更と同じ粒度**になる。

## 2. インスペクタのロック

### 2-1. 何が止まって何が止まらないか

ヘッダー右端の鍵アイコンを ON にすると、**表示対象の切り替えだけ**が止まる。

| 操作 | ロック中の挙動 |
|---|---|
| ヒエラルキー／ビューポートで別アクターを選ぶ | インスペクタは切り替わらない（選択自体は通常どおり動く） |
| ランタイムからの `SELECTED` 通知 | ロック対象以外は無視 |
| ロック対象の値がランタイム側で変わった | **反映される**（`ACTOR_COMPONENTS` の受信は止めない） |
| ロック対象自身の再選択 | そのまま通す（表示は変わらない） |

入口は 2 か所だけ：`SelectActor(dfsId)` と `OnSelectionChanged(id)`。
どちらも先頭でガードを 1 行呼ぶ形にしてあり、他の経路を増やさない。

### 2-2. 自動解除

DFS ID は**ツリーの走査順そのもの（＝位置）**なので、手前のアクターが増減すると
同じ ID が別のアクターを指す。取り違えて別アクターを編集させるのが一番まずいので、
ロック時に **DFS ID と名前**を控え、`HIERARCHY` が届くたびに
「その ID の位置に、同じ名前のアクターがいるか」を確かめる。

| 状況 | 挙動 |
|---|---|
| 同じ ID に同じ名前 | 継続 |
| 名前が違う／ID が無い（削除・ID ずれ） | **解除**して未選択表示へ戻す |
| `HIERARCHY_RESET`（シーン遷移・Play 停止の復元・`LOAD_SCENE`） | **解除** |
| モード切替（シーン編集 ⇔ アクター編集） | **解除** |

「同じ名前のノードを探して追従する」ことも考えられるが、同名アクターは珍しくないため、
削除直後に別の同名アクターへ乗り移る危険がある。解除して選び直させる方を採った。

**副作用（既知）**: ロック対象をリネームすると名前一致が崩れるので解除される。
取り違え防止に倒した判断で、実害は「もう一度ロックし直す」だけ。

名前は**ランタイムから来た生の名前**（`ACTOR_COMPONENTS` の `name`）を使う。
ヘッダーの表示テキストは名前が空のとき `Actor #3` に置き換わるため、
そちらを控えると `HIERARCHY` のノード名と決して一致しない。

### 2-3. 状態

セッション内のみ。`editor/settings/` にもレイアウトにも保存しない。
鍵トグルはアクターを表示しているときだけ出す。

## 3. Transform / CanvasTransform のスケール連動

### 3-1. 動き

スケール行の右端にある鎖アイコンを ON にすると、
**どのチャンネルを編集（入力・ドラッグ）しても他のチャンネルが同じ比率で変わる**。

- 3D Transform … X / Y / Z の 3 チャンネル
- 2D CanvasTransform … X / Y の 2 チャンネル

例: `(2, 4, 1)` の X を 2 → 3 にすると `(3, 6, 1.5)`。

### 3-2. 0 の扱い

| 状況 | 結果 |
|---|---|
| 他チャンネルの元の値が 0 | そのチャンネルは**編集したチャンネルと同じ値**にする（0 × 比率 では永久に 0 のままのため） |
| 編集したチャンネルの元の値が 0 | 比率そのものが定義できないので**全チャンネルを編集後の値で揃える** |
| 編集後の値が NaN / ∞ | 他チャンネルは触らない |

### 3-3. どこに割り込むか（Undo が 1 操作になる理由）

連動は `CommitTransform()` の入口 **1 か所**でだけ行う。
入力確定（Enter / フォーカス喪失）・数値ドラッグ・軸ラベルドラッグは
すべて最終的に `CommitTransform()` を通るため、そこで他チャンネルのテキストを
書き換えてから送信すれば、

- IPC は従来どおり 1 通（`SET_ACTOR_TRANSFORM` / `SET_TRANSFORM` / `SET_CANVAS_TRANSFORM`）
- ランタイム側の Undo も 1 操作

になる。フィールドごとに送信を足すと経路が二重になるので、そうしない。
ドラッグ中の Undo まとめは既存の `BEGIN_TRANSFORM_DRAG` / `END_TRANSFORM_DRAG` がそのまま効く。

### 3-4. 基準値（baseline）とドラッグ

比率は「編集前の値」からしか求まらない。ドラッグ中は 1 ピクセル動くごとに
`CommitTransform()` が呼ばれるので、その都度「直前の値」を基準にすると
比率の掛け算が積み重なり、表示桁への丸めでじわじわずれる。

そこで、

- スケール行を組み立てた時点で基準値を控える
- **ドラッグ（マウスキャプチャ）が続く間は基準値と編集チャンネルを固定**し、毎回そこから絶対値で計算する
- ドラッグが終わったら基準値を取り直す

としている。編集チャンネルの特定は「基準値と比べてちょうど 1 つだけ変化しているか」で行い、
0 個（位置・回転など別の行の編集）や 2 個以上（基準値が古い）のときは**連動せず基準値を取り直す**。
ユーザーが触っていない値を勝手に書き換えないための門番。

連動先の表示桁数は編集中フィールドに合わせる（ドラッグ中は刻み幅で桁数が変わるため）。

### 3-5. 状態

アクターごとではなく**エディタのセッション内で 1 つ**。Transform 用と CanvasTransform 用で別々。
永続化しない。ビューポート所属ルートキャンバス（Transform 恒等固定）では
グリッドごと不活性になるため、トグルも押せない。

## 4. テスト

`editor/tests/InspectorLogicTests`（`dotnet run` で実行できる素のコンソール）。

- 画像比率: 縦基準 / 横基準 / 正方形 / 画像寸法 0 / 保つ辺 0 / 反転（負値）の符号 / 非有限
- スケール連動: 比率適用 / 0 のチャンネル / 編集チャンネルが 0 / 2 チャンネル / 負比率 / 非有限 /
  固定基準からの再計算がずれないこと
- 編集チャンネルの特定: 1 つ / 0 個 / 2 個以上 / 要素数違い / 誤差未満
- 表示桁数と整形（不変カルチャ固定）

UI 側（トグルの見た目・メニュー・グリッド配置）は自動テストの対象外。
XAML の実行時エラーはヘッドレス起動（`--headless`）でパネル生成まで通ることで確認する。
