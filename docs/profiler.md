# プロファイラ（フレーム内セクション別 CPU 時間計測）

> このドキュメントがプロファイラ機能の**正典**です。実装と食い違う記述を見つけたら、
> ソースを読んで本ファイルを更新してください。

エディタの「プロファイラ」パネルで、**1 フレームのどの階層・どのセクションに何 ms 掛かっているか**を
階層ツリーで確認できます。ランタイム（Rust）側でフレームループの各区間を計測し、0.5 秒ごとに
集計結果をエディタへ送って表示する構成です。

---

## 1. 使い方（3 ステップ）

1. エディタの **「表示 → パネル → プロファイラ」** を選ぶ（初回は下部の Project / Output と同じ
   ペインにタブとして出ます。ドラッグで好きな位置へドッキングできます）。
2. パネルが表示された瞬間から計測が始まり、**約 0.5 秒ごと**に表示が更新されます。
   Edit モードでも Play モードでも計測されます。
3. 見終わったらパネルを閉じる（または他のタブへ切り替える）。**閉じている間は計測自体が止まり、
   オーバーヘッドはゼロになります。**

### パネルの見方

| 表示 | 意味 |
|---|---|
| **セクション名** | 計測区間の名前。ツリーの親子＝呼び出しの入れ子 |
| **平均 ms** | 1 フレームあたりの平均時間。**毎フレーム走らない処理は按分されます**（例: 5 フレームに 1 回 10ms なら 2.00） |
| **最大 ms** | 集計窓（0.5 秒）内で最も重かった 1 フレームでの時間。**スパイクはここに出ます** |
| **自己 ms** | 平均 ms から子セクションの平均 ms 合計を引いた値。**そのセクション自身が消費した時間** |
| **比率 %** | フレーム全体（`Frame`）に対する割合 |
| **回数** | 1 フレームあたりの平均呼び出し回数（`ConstantUpdate` が複数回回っている等が分かる） |

行の色は「平均 ms」で決まります（しきい値は `ProfilerPanel.xaml.cs` で定数化）。

| 色 | 条件 |
|---|---|
| 通常（薄いグレー） | 平均 2.0ms 以下 |
| 黄（`#E5C07B`） | 平均 2.0ms 超 |
| 赤（`#FF6B6B`） | 平均 5.0ms 超 |

**ツールバー**

- **一時停止**: 表示を凍結します（受信データを捨てるだけで、計測自体は続きます）。
  スパイクの瞬間を落ち着いて読むために使います。
- **並び順**: 「実行順」（既定・JSON の並び＝フレーム内で実行される順）/「合計時間順」（平均 ms 降順）/
  「自己時間順」（自己 ms 降順）。**まず「自己時間順」で見ると犯人が最上位に来ます。**
- **概況**: `FPS: 59.9  フレーム: 16.7ms (最大 22.1ms)  窓: 30 フレーム`

**グラフ**: 直近 240 サンプルのフレーム時間推移（折れ線）。破線は 60fps（16.67ms）のガイドライン、
縦軸は「実測最大値と 33.3ms（30fps）の大きい方」でオートスケールします。

ツリーの**展開状態はパネル側で保持**されるので、0.5 秒ごとの更新で勝手に開き直したりしません
（`HierarchyPanel` の折りたたみ記憶と同じ方式：閉じたノードの名前パスを覚えておき復元する）。

## 2. 計測方式

### 2.1 スコープ計測（RAII）

計測は**サンプリングではなくスコープ計測**です。ソースへ仕込んだスコープの生存期間を
`Instant` 2 回で測り、入れ子をそのままツリーにします。

```rust
{
    crate::profile_scope!("地形/草バッファ再構築");
    self.rebuild_grass_gpu(&device, &queue);
}   // ここでスコープが閉じ、経過時間が記録される
```

ブロック境界と計測区間が一致しない場所（フレームループのように、区間の開始と終了が
巨大な関数の別々の場所にある場合）は、ガードを直接持って明示的に閉じます。

```rust
let _prof_ipc = ScopeGuard::new("IPC 処理");
self.process_ipc(event_loop);
drop(_prof_ipc);
```

**「どの関数が重いか」は、計装済みセクションの粒度で答えます。**
サンプリングプロファイラ（一定間隔でコールスタックを採取する方式）は**対象外**です。
より細かい粒度が必要になったら、その関数へ `profile_scope!` を 1 行足してください
（＝計装を増やす形で粒度を上げる設計です）。

### 2.2 同名スコープのマージ

同じ親の下で同じ名前のスコープが 1 フレーム中に複数回実行された場合、**1 行にマージ**され、
合計時間と呼び出し回数が加算されます。ループの中に計装しても行が増殖しません。

### 2.3 スレッド

計測はメインスレッド（フレームループ）専用です。フレーム記録はスレッドローカルで、
`frame_begin()` を呼んだスレッドだけが計測対象になります。rayon ワーカー等の別スレッドで
`profile_scope!` が実行されても完全な no-op です（バッファが増え続けることもありません）。

### 2.4 上限（暴走防止）

| 上限 | 値 | 超えたら |
|---|---|---|
| 1 フレームのノード数 | 4096 | それ以降のスコープは計測されない |
| ネスト深さ | 64 | それ以上深いスコープは計測されない |
| スクリプトから渡す名前の種類 | 256 | それ以降の新しい名前は計測されない |

## 3. オーバーヘッド設計

**計測は既定で無効です。** エディタの「プロファイラ」パネルが表示されている間だけ、
`SET_PROFILER:1` がランタイムへ届いて有効になります。

| 状態 | `profile_scope!` 1 回のコスト |
|---|---|
| 無効（パネルを開いていない） | `AtomicBool` の Relaxed ロード 1 回 + 分岐のみ。`Instant` も取らない |
| 有効 | `Instant::now()` × 2 + 同名子ノードの線形探索 + `Vec` の push/pop |

- ノード名は `&'static str` なので、記録時に文字列の確保やコピーは発生しません。
- 記録バッファ（`Vec`）はフレーム間で使い回すため、定常状態ではヒープ確保が起きません。
- **エディタへの送信は毎フレームではなく集計窓（0.5 秒）ごとに 1 回**です。

### 既存の `SEED_PERF_LOG` との関係

フレームループには以前から `perf_*` 変数によるログ用計測（環境変数 `SEED_PERF_LOG` で
`[PERF]` 行を出す仕組み）があります。**同じ区間を二重に計測しないため、プロファイラのスコープは
既存タイマと同じ区間の開始・終了へ相乗りさせています**（`ScopeGuard::new` を既存の
`Instant::now()` の隣に置き、`elapsed()` を取る行の直前で `drop`）。
既存の `[PERF]` ログはそのまま残しています（コンソールで一発確認したいとき用）。

実装は `runtime/src/engine/core/app_base/app/frame_renderer.rs`（フレームループ本体）。
ツリーのルートは常に `Frame`（フレーム全体）です。

│   ├─ スクリプト/Update
│   ├─ スクリプト/ConstantUpdate          … 固定ステップ。回数列で「追いつき」が分かる
│   ├─ スクリプト/LateUpdate
│   └─ スクリプト/Render

│   ├─ 描画/シャドウ深度パス
│   ├─ RT/TLAS・BLAS ビルド

> （§7 参照）。GPU が詰まっているときは `描画/BeginFrame` か `描画/Submit・Present` が伸びます。

## 5. スクリプトから任意区間を計測する

C# スクリプトから `SEED.Profiler` で自分のコードを計測できます。計測結果は
「そのとき実行中のセクションの子」として現れます（例: `スクリプト > Update > 敵の索敵`）。

```csharp
public void Update()
{
    using (SEED.Profiler.Scope("敵の索敵"))   // 推奨: 例外で抜けても確実に閉じる
    {
        SearchEnemies();
    }

    SEED.Profiler.Begin("経路探索");           // 明示的に書くなら Begin/End を対にする
    SolvePath();
    SEED.Profiler.End();
}
```

- パネルを開いていない間はほぼゼロコストで `false` を返します（文字列変換もしません）。
- **名前は固定文字列にしてください**（名前の種類の上限 256 に達すると計測されなくなります）。
- `Begin` / `End` の対応が崩れてもエンジン側の計測は壊れません。`End` は「自分が開いた区間」しか
  閉じず、閉じ忘れた区間は親スコープの終了時にまとめて閉じられます。

API の詳細は `docs/scripting_api.md` の 7.6 節。

## 6. 実装（メンテナ向け）

### ファイル構成

| ファイル | 役割 |
|---|---|
| `runtime/src/engine/core/profiling/mod.rs` | 有効／無効の切り替え、フレーム開始・終了、名前のインターン |
| `runtime/src/engine/core/profiling/scope.rs` | `ScopeGuard` / `profile_scope!` / スレッドローカルのフレーム記録 |
| `runtime/src/engine/core/profiling/aggregate.rs` | 集計窓（0.5 秒）への畳み込み（平均・最大・回数） |
| `runtime/src/engine/core/profiling/report.rs` | 集計結果 → 1 行 JSON |
| `runtime/src/engine/core/app_base/app/frame_renderer.rs` | 計装の設置場所（§4） |
| `runtime/src/engine/core/scripting/host_api.rs` | `ffi_profiler`（`SEED.Profiler` の FFI） |
| `scripting/src/Api/Profiler.cs` | C# 側 API（`Begin` / `End` / `Scope`） |
| `editor/src/Panels/ProfilerPanel.xaml(.cs)` | パネル本体 |
| `editor/src/Runtime/RuntimeManager.cs` | `SET_PROFILER` 送信と `PROFILER:` 受信 |

### IPC プロトコル

行区切りテキスト（1 行＝1 メッセージ）です。

**エディタ → ランタイム**

```
SET_PROFILER:1    … 計測を有効化（パネルを表示したとき）
SET_PROFILER:0    … 計測を無効化（パネルを非表示にしたとき）
```

無効化時は集計器ごと破棄されるため、次に有効化したときに古い窓のデータが混ざりません。
ランタイムを起動／再接続／Play 開始したタイミングでは、エディタが現在の購読状態を再送します
（さもないとランタイム側が計測 OFF のままになり、パネルを開き直すまでデータが止まります）。

**ランタイム → エディタ**（集計窓ごとに 1 回）

```
PROFILER:{"frames":30,"window_ms":501.2,"fps":59.9,"frame_avg_ms":16.7,"frame_max_ms":22.1,
          "samples":[16.2,16.9,…],
          "root":{"name":"Frame","avg_ms":16.7,"max_ms":22.1,"self_ms":2.1,"share":100.0,
                  "calls":1.0,"calls_total":30,"children":[ … ]}}
```

| フィールド | 意味 |
|---|---|
| `frames` | 集計窓に含まれたフレーム数 |
| `window_ms` | 窓の実経過時間（ms） |
| `fps` | 窓内の平均フレームレート |
| `frame_avg_ms` / `frame_max_ms` | フレーム全体の平均／窓内最大（ms） |
| `samples` | 各フレームの所要時間（ms、実行順）。推移グラフ用 |
| `root` | セクションツリーのルート（名前は常に `Frame`） |

セクションノード: `name` / `avg_ms` / `max_ms` / `self_ms` / `share`(%) / `calls`（1 フレームあたり平均）/
`calls_total`（窓内合計）/ `children`（実行順）。

### 計装を増やすには

1. 計測したい関数・ブロックの先頭に `crate::profile_scope!("カテゴリ/名前");` を 1 行足す。
   ブロック境界と区間が一致しないなら `ScopeGuard::new(...)` ＋ `drop(...)` を使う。
2. 名前は `&'static str` のみ（動的な文字列は行の増殖を招くため受け付けません）。
   既存の命名に合わせて `カテゴリ/詳細`（`描画/…`、`物理/…`、`地形/…`、`水/…`、`スクリプト/…`、`RT/…`）とする。
3. 本ファイル §4 のツリー図へ 1 行追記する。

## 7. GPU 時間の計測（未実装 / phase 2 申し送り）

**現状、パネルに出るのはすべて CPU 時間です。**「描画/○○」はコマンドバッファへの
**記録時間**であり、GPU が実際にそのパスを実行した時間ではありません。

### 見送った理由

本エンジンはデバイス生成時（`runtime/src/engine/core/renderer/mod.rs` の
`required_features`）に `wgpu::Features::TIMESTAMP_QUERY` を要求しておらず、
各パスの `timestamp_writes` はすべて `None` です。GPU 時間を出すには以下が必要で、
今回の範囲（CPU 側の階層可視化）に対して変更量とリスクが見合わないと判断しました。

### 実装するときの手順（phase 2）

1. `required_features` へ `TIMESTAMP_QUERY`（対応 GPU のみ。`adapter.features()` で分岐する。
   RT やバインドレスと同じ「対応していれば足す」パターンに従う）。
   パス内の任意点を測るなら `TIMESTAMP_QUERY_INSIDE_PASSES` も要る。
2. パス数 × 2 個のクエリを持つ `QuerySet` と、解決先の `QUERY_RESOLVE | COPY_SRC` バッファ、
   読み戻し用の `MAP_READ` ステージングバッファをフレームごとに用意する（多重フライト対応のため
   2〜3 フレーム分をリングで持つ）。
3. 各 `begin_render_pass` / `begin_compute_pass` の `timestamp_writes` へ
   `beginning_of_pass_write_index` / `end_of_pass_write_index` を割り当てる。
   本エンジンのパスは `frame_renderer.rs` に直書きされているため、
   「パス名 → クエリ添字」の割り当て表を 1 か所に集約するのが望ましい。
4. `submit` 後に `resolve_query_set` → `copy_buffer_to_buffer` → `map_async`。
   **結果は 1〜2 フレーム遅れて届く**ので、Hi-Z オクルージョン読み戻しと同じ
   「前フレームの結果を今フレームに反映する」方式にする。
5. `queue.get_timestamp_period()` を掛けて ns へ変換し、CPU 側と同じ集計器へ
   別系統（GPU 用の列）として積む。パネルへは `gpu_ms` 列を追加する。

それまでの間、GPU 律速かどうかは次の 2 セクションで見当を付けられます。

- **`描画/BeginFrame(スワップチェーン取得)` が伸びている** … GPU が前フレームを描き終えるのを
  待っている（＝GPU 律速、または VSync 待ち）。
- **`描画/Submit・Present` が伸びている** … 同上（ドライバ側のキュー詰まり）。
- CPU 側の記録時間（`描画/G-Buffer パス` 等）が伸びていれば、そちらは純粋に CPU 律速です。

## 8. 既知の制限

- **CPU 時間のみ**（§7）。
- **メインスレッドのみ**。物理スレッド・rayon ワーカー内部の時間は、それを待つ側の
  セクション（`物理/3D 同期` など）の時間として現れます。
- **早期 return したフレームは集計に入りません**（描画一時停止中・最小化中・サーフェスエラー時）。
  次フレームの記録開始時に破棄されるだけで、破綻はしません。
- `平均 ms` は**窓内の全フレームで按分**した値です。「実行されたフレームでの平均」ではないため、
  数フレームに 1 回しか走らない処理は小さく見えます。スパイクの実体は `最大 ms` と `回数` で読んでください。
