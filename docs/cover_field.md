# 地表カバー場（Cover Field）— 正典

Phase **I3.1**（積もる基盤）＋ **I3.2**（轍・足跡と Y 照合）。
地形の表面へ「雪・落ち葉の絨毯・泥・濡れ」を積もらせ、その上を歩いた痕を残す仕組み。
本書がこの機能の正典であり、方式の再検討は明示的な要求があったときのみ行う。

関連: `docs/water_interaction_roadmap.md` §I3ロードマップ / `docs/terrain.md`（地形本体） /
`docs/rendering_flow.md`（3層モデル）。

---

## 1. 何を作ったか（1 段落）

地形チャンク（3 次元インデックス・既定 16m 立方）に紐づく **低解像度の永続テクスチャ**
（既定 32×32／チャンク）へ「素材 ID ＋ 量」を 1 層だけ持たせ、
`CoverEmitterComponent` が毎フレーム／シミュレート時にそこへ積算する。
描き手（エミッタ）は地形を知らず、地形シェーダは素材の意味を知らない。
表現の差（雪か落ち葉か濡れか）は **`assets/terrain/cover_materials.json` の数値差だけ**で作る。

---

## 2. 設計判断とその根拠

### 2.1 解像度は 32×32／チャンク（低解像度で足りる）

カバーは「面の性質」であって模様ではない。細かい模様は地形レイヤと素材テクスチャの担当で、
カバー場に要るのは「どこにどれだけ積もったか」という滑らかな分布だけである。

既定チャンク（`voxel_size 0.5m × chunk_cells 32` = 16m）で 32×32 は **0.5m 刻み**となり、
これは既定のメッシュ頂点間隔とちょうど一致する。つまり
**頂点へ載せる段階で情報が一切落ちない最小の解像度**である。これ以上上げても絵は変わらない。

- 定数: `COVER_FIELD_RESOLUTION`（`runtime/src/engine/terrain/cover/field.rs`）
- メモリ: 1 チャンク 32×32×2 バイト = **2 KB**。既定の地面 48 チャンクで 96 KB。

### 2.2 積算は CPU（GPU コンピュートを採らなかった理由）

1 チャンク 1024 テクセル、既定 48 チャンクで 5 万テクセル弱。1 テクセルあたりの計算は
数個の乗算と比較だけである。一方 GPU 化すると:

- 保存（`.tcover`）のたびにテクスチャの **読み戻し（非同期マップ）** が要る
- 「シミュレートボタンで N 秒ぶんを即時計算」が GPU の往復回数ぶんフレームを跨ぐ
- 傾斜ルール・置き換え規則を GPU 側にも書くことになり、ユニットテストできなくなる

積算・保存・テストを 1 本の同期コードで完結させるほうが、この規模では明確に有利。
実測は `SEED_PERF_LOG=1` の `[PERF f=...] cover=...ms` で監視できる。
（後日 GPU 化が必要になっても、純粋関数 `accumulate_chunk` の置き換えだけで済む形にしてある。）

### 2.3 描画は「頂点への焼き込み」＋「フラグメントでの合成」の 2 段

| 何を | どこで | なぜ |
|---|---|---|
| 変位（盛り上げ） | **CPU が頂点位置へ焼く** | 頂点シェーダでやると G-Buffer パス専用になり、シャドウマップ・深度・ID パス・RT の BLAS と形状がズレる（雪が影を落とさない／雪の下に地面が透ける）。位置そのものへ焼けば頂点バッファを共有する全パスが自動的に一致する |
| 法線 | **CPU が頂点法線へ焼く**（カバーの高さ場の勾配で摂動。§3.5.9） | 位置だけ動かして法線を据え置くと凹みに陰影が出ず、痕が輪郭でしか見えない。位置と同じ場所で焼けば形状と陰影が必ず一致する |
| 色・粗さ | **フラグメントシェーダ** | 頂点へ焼くと素材の粗さが運べず、地形レイヤとのブレンドもできない |

頂点が運ぶのは「量」と「素材番号」だけで、地形では未使用だった **`uv0` を転用**している
（`uv0.x = 量(0..1)` / `uv0.y = 素材添字`）。これは T2 でレイヤ重みを `Vertex.color` へ
smuggle したのと同じ判断であり、22 パイプラインが共有する 72 バイトの頂点レイアウトを
1 バイトも増やさずに済む。

**量 0 のフラグメントはシェーダの分岐に入らないため、カバー場を持たない地形は
カバー機能導入前とビット単位で同一の出力になる**（コストも `uv0` の読み取りと比較 1 回だけ）。

素材表（色・粗さ）は地形レイヤ uniform（group3）へ同居させた。全チャンク共通のデータなので
**チャンクごとのバインドグループもテクスチャも増えない**（`max_bind_groups = 5` の制約に触れない）。

### 2.4 素材は文字列 ID で参照する

`cover_materials.json` の並び替えで既存シーンの指し先がずれないよう、
`CoverEmitterComponent.material_id` は **添字ではなく `id` 文字列**でカバー素材を参照する
（`props.json` が添字参照で持っている弱点を最初から避けている）。
カバー場の中では u8 の添字で持つが、ID → 添字の解決は `CoverMaterialSet::index_of` 1 か所だけ。

### 2.5 地表情報は密度場から作る（メッシュからではない）

傾斜ルールに使う地表法線と高さは、**密度場（SDF）から直接**導出する（`CoverSurface::from_chunk`）。
描画メッシュから作ると LOD で頂点密度が変わるため、カメラが近づいただけで積もり方が変わってしまう。
密度場は LOD に依らない唯一の真値である。

**air / solid の判定はマーチングキューブと厳密に同じ不等号にする**
（`density < iso` ⇒ SOLID、`density >= iso` ⇒ AIR）。等号の置き場所が 1 つずれると、
「面情報を持つチャンク」と「そのセルのメッシュを出すチャンク」が Y 方向に 1 段ずれ、
積もった雪がどの頂点にも焼かれずに消える。既定の平坦地面（`density = ワールド Y`、
面がちょうど y=0 ＝チャンク境界）がまさにこの境界例である。
回帰テスト: `cover_surface_chunk_matches_mesh_chunk`。

### 2.6 変位の読み取りは「ワールド横断」で行う（チャンク境界に隙間を作らないため）

チャンク境界の上にある地形メッシュの頂点は、隣り合う 2 チャンク（角では 4 チャンク）の
メッシュへ **複製**されている。変位は頂点位置へ焼く（§2.3）ので、
複製された頂点どうしが違う量を読んだ瞬間に別々の場所へ動き、**メッシュに隙間が開く**。

そのため、カバー場の読み取りは 1 チャンク単体ではなく
**自チャンク＋XZ 隣接 8 チャンク**の 3×3 ビュー（`CoverNeighborhood`）で行う。

| | 旧（不具合） | 現在 |
|---|---|---|
| 境界の読み方 | 自チャンクのテクセルへ**クランプ** | 隣チャンクのテクセルを**実際に読む** |
| チャンク A の u=1.0 | 自分のテクセル 31 | 自分の 31 と隣の 0 を tx=0.5 で混ぜる |
| チャンク B の u=0.0 | 自分のテクセル 0 | 隣（A）の 31 と自分の 0 を tx=0.5 で混ぜる |
| 結果 | **別の値**＝段差・隙間 | **同じ 4 テクセル・同じ重み・同じ演算順序**＝f32 のビット単位で一致 |

これは水面グリッド（W5.1）で境界線の共有点を厳密に一致させたのと同じ原則
＝**共有される点は、どちらの所有者から見ても厳密に同じ値を読む**。

- **隣接チャンクにカバー場が無い場合は「量 0」として読む**。「まだ雪が降っていない隣」と
  「そもそもチャンクが無い世界の端」を区別しない。どちらも 0 なので両側から読んだ値は必ず一致する
  （世界の端では最後の半テクセルぶんだけカバーがなだらかに 0 へ落ちる）
- 上下（Y）方向の隣は**混ぜない**。上下段は別の面を持つため、混ぜると洞窟の床へ地表の雪が漏れる
- カバー場が変化したチャンクは、**XZ 隣接 8 チャンクも一緒に焼き直す**
  （`queue_cover_apply`）。片側だけ新しい値で焼くと、その境界だけ食い違って隙間が開くため
- 回帰テスト: `boundary_sample_is_bit_identical_between_neighbours`（辺）/
  `corner_sample_is_bit_identical_between_four_chunks`（角）/
  `accumulated_boundary_is_bit_identical_across_two_chunks`（積算経路込み）

### 2.7 焼き直しは「波」で分散する — カバー場を凍結してから焼く

§2.6 の境界整合は「**両側のメッシュが同じ世代のカバー場を読む**」ことが前提である。
素直に実装すると「隣り合うチャンクを別フレームに焼いてはいけない」という制約になり、
旧実装はこれを **26 近傍で連結した待ちチャンクの塊は分割しない**というスケジューリング
規則で守っていた。

だがこの規則は**全域降雪でまったく機能しない**。エミッタが Global なら全チャンクが同時に
変化して 1 つの巨大な連結成分になるため、フレーム予算（4 チャンク／フレーム）が
迂回され、積算ティックのたびに**全チャンクを 1 フレームで焼く**ことになる。

現在は制約の守り方をスケジューリングから**データの凍結**へ移した。

| | 旧 | 現在 |
|---|---|---|
| 境界整合の担保 | 連結成分を分割しない | 焼き直し開始時にカバー場をクローンして凍結（`CoverBakeWave`） |
| 全域降雪での予算 | 効かない（全件 1 フレーム） | 効く（`COVER_BAKE_CHUNK_BUDGET_PER_FRAME` で頭打ち） |
| チャンクが読む値 | 実データ（`TerrainState::cover`。焼いている間も積算で動く） | 凍結データ（波の全期間で不変） |

**波（`terrain/cover/bake_wave.rs`）**は 1 回ぶんの焼き直し作業単位で、
「対象チャンク ∪ その 26 近傍」のカバー場を丸ごと凍結して保持する。
波に属するチャンクは何フレームに分かれて焼かれても凍結データだけを読むため、
分割しても境界はビット単位で一致する（回帰テスト
`frozen_wave_keeps_boundary_identical_across_frames`）。

- 凍結の費用は 1 チャンク約 7KB（32×32 ×（素材 1B ＋ 量 1B ＋ 踏み固め 1B ＋ 基準 Y 4B））。
  既定の地面 48 チャンクを全部凍結しても 350KB 程度で、積算間隔ごとの memcpy として無視できる。
  波が閉じた時点で解放する
- **波をまたいだ整合**も保たれる。`queue_cover_apply` が「変化したチャンクとその 26 近傍」を
  必ずセットで積むため、境界頂点が読むカバー場のどれかが変化していれば、その境界の
  両側とも次の波の対象に入る
- **波の中断**は 2 つ。轍スタンプが来たら応答性優先で波を張り直す（未処理分は待ち集合へ戻す）。
  地形が再メッシュされたチャンクは基準 Y の前提が崩れるので、26 近傍ごと波から追い出して
  待ち集合へ戻す（`invalidate_cover_for_remesh`）
- 予算の割り当ては `terrain/cover/bake_schedule.rs`。優先度は
  ①轍スタンプ由来（予算外で必ず今フレーム）②カメラ近傍 ③遠方

### 2.8 焼き込みは「その場更新」であり、下流を作り直さない

カバーの変位は**既存頂点への上書き**（頂点数・インデックス列は不変。位置を法線方向へ
押し出して法線を引き直すだけ）である。Marching Cubes の再実行は原理的に不要で、
実際に `apply_cover_to_chunk` は
CPU モデルを差し替えて **`queue.write_buffer` 1 回**で GPU 頂点バッファを書き直すだけ。
再メッシュ・コライダー（Rapier QBVH）再構築・LOD 再生成のいずれも通らない
（物理コライダーは「素の地形」のまま＝雪の厚みは当たり判定に含まれない。意図した仕様）。
回帰テスト `cover_bake_preserves_vertex_count_and_indices`。

下流への波及も「構成（レイアウト）」と「内容」で分ける。

| 世代 | 何を表すか | 誰が見るか | カバー焼き込みで変わるか |
|---|---|---|---|
| `MergeBatchGate`（インスタンス入力） | どのインスタンスをどの行列・ID・タグで描くか | 統合バッチ更新のスキップ判定 | **変わらない**（スキップ継続） |
| `InstancedModelBatch::content_generation` | 実際に描かれる内容 | 影の静的カスケードスキップ（`shadow.rs`） | **変わる**（`note_geometry_changed`） |

したがってカバーの焼き込みは

- 統合バッチ（`shared_model_batches`）を**捨てない**。捨てると次フレームに
  `create_instanced_batch` ＋ 初回 `update()`（rayon 行列再計算・全ノードバッファ書込）が
  走り、ついでに `content_generation` も変わって影の静的スキップまで無効化される
  ——これが「降雪中に統合バッチ再構築とシャドウ深度が毎フレーム走る」原因だった
- 代わりに `note_geometry_changed()` で**内容世代だけ**を進める。形状が変わったチャンクを
  含むカスケードだけが深度を焼き直し、変化の無いカスケードはスキップされ続ける
- RT BLAS は従来どおり `rt_blas_prune_pending` 経由で件数予算つきに捨てて作り直す（§7-2）

> 副作用として、統合バッチが持つ `cpu_model`（カリング用のローカル AABB）はカバーの
> 変位ぶん（既定の雪で数 cm）だけ古いままになる。オブジェクト単位の視錐台カリングは
> 廃止済みで、影のキャスターカリングに使う AABB が数 cm 小さくなるだけなので実害は無い
> （頂点ペイントの高速パスが以前から持っているのと同じ性質）。

## 3. データモデル

### 3.1 純粋データ層 `runtime/src/engine/terrain/cover/`

ECS / GPU / ファイル IO への依存を一切持たない（JSON 文字列 in / 構造体 out、bytes in / bytes out）。

| ファイル | 責務 |
|---|---|
| `material.rs` | `CoverMaterial` / `CoverMaterialSet`（cover_materials.json の定義と正規化） |
| `field.rs` | `CoverField`（素材＋量の 1 層）・`CoverNeighborhood`（3×3 チャンク横断の読み取り）・`CoverSurface`（地表情報）・傾斜ルール |
| `emit.rs` | `CoverEmitSpec` / `CoverEmitRange`（Global / Region / TextureMask）の範囲評価 |
| `accumulate.rs` | `accumulate_chunk`（場 × 地表 × エミッタ × dt → 新しい場） |
| `bake_schedule.rs` | `plan_cover_bake`（焼き直しの件数予算と優先順。§2.7） |
| `bake_wave.rs` | `CoverBakeWave`（カバー場を凍結した焼き直し作業単位。§2.7） |
| `tcover.rs` | `.tcover` のバージョン付きバイナリ永続化 |
| `tests_cover.rs` | 契約テスト（傾斜・置き換え・往復・エミッタ無し＝完全不変） |

### 3.2 カバー素材（`assets/terrain/cover_materials.json`）

```json
{
  "materials": [
    { "id": "snow", "name": "雪",
      "albedo": [0.86, 0.90, 0.95], "roughness": 0.75, "displacement": 0.22 }
  ]
}
```

| フィールド | 意味 |
|---|---|
| `id` | 一意なキー。`CoverEmitterComponent.material_id` から参照する |
| `name` | 表示名（エディタ用） |
| `albedo` | リニア RGB。量 1.0 でこの色へ完全に置き換わる |
| `roughness` | 0..1。量 1.0 でこの値へ完全に置き換わる |
| `displacement` | 量 1.0 のときに地表を法線方向へ持ち上げる高さ（m）。0 = 盛り上がらない |
| `refill_rate` | 足跡・轍が埋め戻る速度（I3.2） |
| `footprint_persistence` | 足跡の残りやすさ（I3.2） |
| `trample_darkening` | 踏み固めた所をどれだけ暗くするか（I3.2） |
| `rim_ratio` | 踏んだぶんの素材が縁へ押しのけられて盛り上がる比（I3.2 §3.5.9） |
| `trample_cavity` | 溝の中がどれだけ環境光を遮られるか（I3.2 §3.5.9） |

いずれも既定は 0（＝書かなければ従来と同じ挙動）。新しい 2 つを書き忘れた素材が
勝手に地形を膨らませたり暗くしたりしないよう、`displacement` と同じ方針で
「無指定 = 何も起きない」に倒してある。

サンプルは 3 種: `snow`（白・変位あり） /
`wet`（変位ゼロ・アルベド暗く粗さ低下＝雨用） / `mud`。
アセットが読めない場合は組み込み既定（前 2 種＝ `snow` / `wet`）へフォールバックするので、
アセット未整備のプロジェクトでもそのまま動く。

> **`leaf_carpet` は削除済み**: 変位 0.06m は既定の頂点間隔 0.5m に対して傾きが約 7 度にしかならず、
> アルベドも土の地表レイヤと近いため「積もっても見た目が変わらない」素材だった。
> 落ち葉を作りたい場合は `displacement` を 0.15 以上に取り、地表レイヤと明確に差の付く
> アルベドを与えること（§3.5.5 の推奨値を参照）。

> **反映のタイミング**: `cover_materials.json` の変更は **`TERRAIN_RELOAD_LAYERS`**
> （地形設定ウィンドウでレイヤを保存したとき）で反映される。素材表は GPU のレイヤ uniform に
> 同居しており、CPU と GPU を同時に更新できる経路がそこしか無いため。

### 3.3 積算の規則

```
1 テクセル 1 ステップの増分
  delta = 被覆率(エミッタ) × 強度(量/秒) × dt × 傾斜スケール
```

**傾斜ルール** — 法線の上向き成分 `up` で `smoothstep`:

| `up` | 意味 | 積もりやすさ |
|---|---|---|
| ≤ `COVER_SLOPE_UP_MIN` (0.34 ≒ 70°) | ほぼ崖 | 0 |
| `COVER_SLOPE_UP_FULL` (0.87 ≒ 30°) ≤ | 緩斜面 | 1 |
| その間 | — | smoothstep で連続 |

面が無いテクセル（空中・全て個体のチャンク）と非有限値は 0（積もらない）。

**「素材なし」の番兵値は `u8::MAX`**（`COVER_MATERIAL_NONE`）。
以前は `0` であり **1 番目に定義された実素材と添字が衝突**していたため、
「素材なし」のはずのテクセルが 1 番目の素材の踏み固め係数
（`trample_darkening` / `trample_cavity`）を引いて地表を暗くし、環境光まで遮っていた。
`TERRAIN_MAX_COVER_MATERIALS`（16）より大きい値にすることで
`CoverMaterialSet::get()` は必ず `None` を返し、「素材なし＝寄与ゼロ」が構造的に保証される
（回帰テスト `cover_material_none_never_resolves_to_a_real_material`）。

**消しゴムは素材添字を消さない** — `CoverField::erase` は量と轍だけを削る。
量 0 のテクセルは読み取り側が必ず「量 0」として扱うので添字は描画へ寄与せず、
逆に消すと上記の補間で黒縁が出る。置き換え規則（下記）はどちらも `amount != 0` を
前提にしているため、添字を残しても「消した所へ別素材を塗ると 1 ストローク損する」ことは無い。

**素材置き換え規則（1 層仕様の要）** — `CoverField::deposit`:

- 同じ素材（または空のテクセル）→ 単純に加算（上限 1.0 で飽和）
- **違う素材 → まず古い素材の量を `delta` ぶん削る。削り切って余った分だけが新素材として積もる**

これにより「落ち葉の上に雪が降ると、落ち葉が見えなくなってから雪が積もり始める」という
自然な遷移が、1 層しか持たないまま得られる。厚く積もった素材の置き換えには
2 倍の時間がかかる（削る時間 ＋ 積む時間）——これは意図した挙動である。

**自然減衰は無い**（融解・埋め戻し・風化はスコープ外）。積む方向にしか動かないので必ず飽和する。

**量 0 のままなら素材添字も書き換えない** — `deposit` の増分が量子化の粒（1/255）に届かず
量が 0 のままのときは、素材添字も据え置く。以前は「空のテクセル」だからと添字だけを
書き換えており、**見た目が 1 ピクセルも変わらないのにチャンクが「変化あり」になって
毎フレーム焼き直される**原因になっていた（素材違いのエミッタが 2 つ届いていると永久にばたつく）。

#### 積算ティック（性能）

積算は**毎フレームではなく一定間隔のティック**で走る。
間隔は `cover_materials.json` のルート `accumulate_interval_sec`（既定 0.25 秒・`serde default`）で、
値は `CoverMaterialSet::accumulate_interval_sec()` が 1/60〜2 秒へ丸める。

- 60fps の 1 フレームで積もる量は既定強度 0.2/秒なら 0.0033 で、**量子化の粒（1/255 ≒ 0.0039）に
  すら届かない**。つまり毎フレーム走らせても絵は変わらないのに、全チャンク走査と
  エミッタ収集（マスク画像の複製を含む）を払っていた。
- ティック発火時は**貯めた経過時間の全量**をまとめて積む（`advance_accumulate_tick`）。
  積算は `量 += 被覆率 × 強度 × dt × 傾斜` の単調加算なので、
  **総量は毎フレーム積算していたときと一致する**（回帰テスト `accumulate_tick_conserves_total_time`）。
- 連続シミュレートを停止した瞬間は、未消化の端数をその場で 1 回積む
  （押していた時間の最後の 1 ティックぶんが失われないため）。
- **轍スタンプ（`InteractionSource`）はティックの対象外で毎フレーム走る**。
  踏んだ瞬間に凹む応答性が要るためで、そちらは「触れたチャンクだけ」に閉じているので安い。
- 既知のトレードオフ: 積もる量が 0.25 秒ごとに約 1/20 ずつ跳ぶため、
  積雪の立ち上がりは厳密には階段状になる（既定変位 0.22m に対し 1 段 1.1cm）。

**エミッタが届かないチャンクには場を作らない** — `chunk_has_active_emitter`（純関数）で
チャンク AABB との交差を先に判定し、届かないチャンクは `CoverField` の確保も
地表情報の生成も行わない。判定条件は `accumulate_chunk` の早期棄却と同一である
（`emitter_touches_chunk` に 1 本化してあり、テストが一致を固定している）。

### 3.4 `.tcover` フォーマット（TCOVER v2・リトルエンディアン）

`.tvox` / `.tscatter` と同じディレクトリ（シーンの地形フォルダ。既定は `assets/terrain/<scene>/`）に
`chunk_X_Y_Z.tcover` として置く。

| オフセット | 型 | 内容 |
|---|---|---|
| 0 | u8[4] | マジック `"TCOV"` |
| 4 | u32 | バージョン（現在 2） |
| 8/12/16 | i32 ×3 | チャンク座標 x / y / z |
| 20 | u32 | resolution（1 軸のテクセル数） |
| 24 | u8[R×R] | 素材添字（row-major: `ix + iz*R`） |
| 24+R×R | u8[R×R] | 量（0..255 が 0.0..1.0） |
| 24+2R×R | u8[R×R] | 踏み固め深さ（0..255 が 0.0..1.0。**v2 で追加**） |
| 24+3R×R | f32[R×R] | 面の基準 Y（ワールド座標・m。**v2 で追加**） |

- **v1 も読める**（書き出しは常に v2）。v1 は「踏み固め = 全 0 / 基準 Y = 未知」として移行し、
  基準 Y はロード直後に地表情報から再計算される（`sync_cover_base_y`）。
  v1 のシーンを 1 度保存すると v2 へ上がる

- **量 0 のチャンクはファイルを削除する**（残すと次回ロードで消したはずの雪が復活する。
  `.tscatter` と同じ不変条件）
- 解像度が現行と違うファイルは `ResolutionMismatch` として弾く（リサンプルはしない）
- ファイルが無いのはエラーではない（カバー機能より前のシーンをそのまま開ける）

### 3.5 轍・足跡（I3.2）

Play 中に `InteractionSourceComponent` を持つアクタが**動きながらカバーのある地面に接する**と、
その接地点へ「踏み固め」がスタンプされる。降雪が続けば轍は徐々に埋まり、止めば永久に残る。

#### 3.5.1 チャンネル設計（カバー場に足した 2 つ）

| チャネル | 型 | 意味 | 永続化 |
|---|---|---|---|
| `trample` | u8（0..255 = 0.0..1.0） | 踏み固め深さ。**量と同じ単位** | `.tcover` v2 |
| `base_y` | f32（メートル） | そのテクセルの「積もっている面」のワールド Y | `.tcover` v2 |

- **実効の量 = `max(量 − trample, 0)`**。描画（変位も色の混ぜ具合も）はこの実効量だけを見る。
  つまり踏まれた所は盛り上がりが消え、trample が量を超えた所は**下地（地形レイヤ）が露出**する
- 踏み固めは**加算ではなく最大値更新**。同じ場所に立ち続けても穴は掘れず、
  複数のソースが同じテクセルを踏んでも結果は順序に依らない（決定的）
- `base_y` は「量を持つテクセルでは必ず有限」という不変条件を積算側が守る。
  面が無ければ `COVER_BASE_Y_ABSENT`（-∞）

#### 3.5.2 Y 照合 —「面はワールド位置の純関数として選ぶ」

カバー場は XZ の 2 次元なので、素朴に押すと**洞窟の床を歩いた轍が頭上の地表にも付く**。
そこで `base_y` を使い、次の 2 か所で「その点はどの面か」を照合する。

| 場面 | 何と照合するか | 許容差 |
|---|---|---|
| スタンプ（轍を押す） | ソース位置のワールド Y ↔ テクセルの面の高さ（`CoverSurface::surface_y_at`） | **上下非対称**（下記 3.5.2-b） |
| 焼き込み（頂点へ載せる） | 頂点のワールド Y ↔ 上下 3 段の `base_y` のうち最も近いもの | チャンク 1 辺 × 0.5（既定 8m） |

**これが I3.1 §7-8「Y チャンク境界の段差」の恒久対策でもある。**
`CoverNeighborhood` は 3×3 から **3×3×3**（XZ 8 近傍 × 上下 3 段）へ広げ、
4 隅のテクセルごとに「頂点のワールド Y に基準 Y が最も近い段」を選ぶ。
選択規則はワールド位置だけの純関数なので、境界面上の複製頂点を焼く上下 2 つのチャンクが
**同じ段・同じ値**に行き着く（f32 のビット単位で一致）。

- 許容差をチャンク 1 辺の半分にしてあるのが効く理由: 段の間隔はチャンク 1 辺なので、
  1 つ以上離れた段は必ず候補から外れる。よって上段視点・下段視点で
  **候補集合が実質的に一致**し、bit 一致が保証される（同着は必ず下段が勝つよう走査順を固定）
- カバー場が変化したチャンクは **26 近傍**（上下段を含む）も一緒に焼き直す（`queue_cover_apply`）
- 回帰テスト: `y_boundary_sample_is_bit_identical_between_stacked_chunks`（Y 境界）/
  `distant_y_layer_is_not_sampled`（1 段離れた面は読まない）。
  横方向の既存テスト 3 本も 3×3×3 のまま通る
- **基準 Y が 1 段も分かっていない列**（TCOVER v1 を読み込んだ直後など）は
  I3.1 と同じ挙動（自チャンクの段だけを読む）へ縮退する。同期後は必ず上の規則で解決される
- **挙動が変わる点**: 崖の側面のように「面から 8m 以上離れた」頂点はカバーを読まなくなった。
  以前は真上のテクセルの雪が側面へ引き伸ばされていた（I3.1 の副作用）

#### 3.5.2-b 接地スナップ — Y 照合の窓は上下で非対称

**当初の実装は上下対称の窓（`|面の Y − ソースの Y| ≤ 影響半径`）で、実機で
「雪の上でアクタを動かしても轍が一切残らない」不具合を出した。**

原因は「ソースのワールド Y ＝ アクタの `Transform` の原点」であって足裏ではないこと。
人型モデルの原点が腰にある、当たり判定カプセルの中心に置いてある、といった
**ごく普通の構成では原点が地面より 1m 前後高い**。既定の影響半径 1m ではぎりぎり、
足跡サイズ（0.3〜0.5m）に絞ると確実に窓の外へ落ち、1 テクセルも押されなかった。

そこで窓を次の非対称なものへ変えた（`CoverStampSpec::matches_surface_y`）。

```
面の Y − ソースの Y  ≤  y_tolerance()        … 上方向（= max(半径, 0.25m)）
面の Y − ソースの Y  ≥ −ground_reach_down()  … 下方向（= y_tolerance() + 2.0m）
```

- **下方向だけを広げる**のが要点。上方向を同じだけ広げると
  「洞窟の床を歩いた轍が頭上の地表に付く」という、Y 照合がそもそも防ぎたかった
  漏れが復活する。物は必ず**面の上に載る**ので、探す向きは下だけでよい
- 下方向の追加距離は `COVER_STAMP_GROUND_SNAP_DROP = 2.0m`。人型（腰 1m 前後）・
  小型車両（車軸中心 0.5m 前後）の原点ずれを飲み込みつつ、
  「2m 上の桟橋を歩いたら下の雪に轍が付く」誤爆までは届かない距離として選んだ。
  これ以上の浮きを許したい場合は**影響半径を大きくする**（許容差が半径に比例して伸びる）
- **チャンク選別（`is_outside_aabb`）も同じ非対称の窓を使う**。ここを対称のままにすると、
  テクセル単位では届く面を持つチャンクが選別の段で先に落ち、修正が効かない
- 回帰テスト（`tests_cover.rs` §7-2。エンジン層のチャンク選別まで含めて再現する）
  - `stamp_reaches_ground_from_raised_actor_origin` … 原点が腰の高さ（0.9m）でも押される
  - `moving_source_leaves_a_trail_of_footprints` … 2m 歩くと経路に沿って轍が続く
  - `ground_snap_stops_beyond_documented_drop` … 探索距離の外側は踏まない
  - `ground_snap_never_stamps_ceiling_above_source` … ソースより上の面は踏まない

#### 3.5.3 スタンプの形状（Circle / Texture）

`InteractionSourceComponent.stamp_shape` で選ぶ。

| 形状 | 落ち方 | 用途 |
|---|---|---|
| `Circle`（既定） | 中心 1.0・縁 0.0 の smoothstep（半径 = `radius`） | 人の足跡・獣の踏み分け |
| `Texture` | グレースケール画像（白 = 最も深い / 黒 = 踏まない） | タイヤのトレッド・靴底の型 |

- `Texture` は**進行方向へ回転して**押される。向きは前フレームからの移動量から求め、
  ほぼ静止（0.05m/s 未満）なら**直前の向きを保つ**（止まった瞬間に痕が回らない）。
  一度も動いていないソースの既定は +Z
- 画像の**上方向（V=0 側）が進行方向**、右方向が進行方向の右手側。
  実寸は `stamp_size = [横幅, 進行方向の長さ]`（メートル）
- 画像の作り方: 背景を黒、痕にしたい部分を白で塗った PNG を用意する。
  タイヤなら「進行方向に伸びる縦長のトレッド模様」、靴底なら「足裏の輪郭」。
  グレーは中間の深さになるので、縁をぼかすと痕がなじむ。R チャンネルだけを読む
  （カラー画像を入れても壊れないが、グレースケールで作るのが分かりやすい）
- **草なびき・水の波紋には形状は効かない**（従来どおり半径の円）。
  インタラクションフィールドはワールド俯瞰の低解像度テクスチャへ「速度」を焼く仕組みで、
  向きを持つマスクを載せるには場のフォーマットごと変える必要がある。
  そもそも「草が踏み分けられる範囲（体の周り）」と「地面に残る痕（接地面）」は別物なので、
  前者が等方なのは意味的にも正しい

#### 3.5.4 埋め戻し（降雪が轍を埋める）

```
1 テクセル 1 ステップの埋め戻し量
  refill = 今このテクセルへ積もった量(delta) + 素材の refill_rate × 被覆率 × dt
```

- **自然減衰は無い**。有効なエミッタがそのテクセルへ降っている間だけ轍は浅くなり、
  エミッタを止めれば轍は永久に残る（時間で勝手に消えない）
- `refill_rate` は「その素材が自分で均される速さ」（雪はさらさら崩れる＝大きめ）

#### 3.5.5 素材ごとの係数（`cover_materials.json`）

推奨値（見栄え強化後の既定。`assets/terrain/cover_materials.json` と組み込み既定の両方）:

| キー | 意味 | snow | wet | mud |
|---|---|---|---|---|
| `displacement` | 量 1.0 での盛り上がり高さ（m） | **0.22** | 0.0 | 0.05 |
| `footprint_persistence` | 足跡の残りやすさ（0..1。0 = 痕が付かない） | 0.9 | **0.0** | 1.0 |
| `refill_rate` | 降っている間に轍が均される速さ（量/秒） | 0.02 | 0.0 | 0.0 |
| `trample_darkening` | 踏み固めた所をどれだけ暗くするか（0..1） | **0.32** | 0.0 | 0.45 |
| `rim_ratio` | 縁の盛り上がり比（0..1） | **0.5** | 0.0 | 0.35 |
| `trample_cavity` | 溝の中の環境光遮蔽（0..1） | **0.7** | 0.0 | 0.6 |

`displacement` を 0.15 → 0.22 へ上げてあるのは、既定の頂点間隔 0.5m に対して
15cm では足跡の壁の傾きが約 17 度にしかならず、陰影として弱かったため。
22cm なら約 24 度になり、真上から照らしても輪郭が立つ。
**この値を下げると轍は再び「跡は付くが地味」へ戻る**（§3.5.9）。

#### 3.5.6 描画（頂点が運ぶもの）

`uv1` も地形では未使用だったので、**踏み固めの 2 スカラー**の運び手に転用した。

```
uv0.x = 実効の量（max(量 - trample, 0)）   uv0.y = 素材添字（**補間安全な添字**。下記）
uv1.x = trample × 素材の trample_darkening（0..1） … アルベドを暗くする
uv1.y = trample × 素材の trample_cavity   （0..1） … G-Buffer の occlusion へ
法線  = カバーの高さ場の勾配で摂動した値（頂点法線そのもの。§3.5.9）
```

- CPU 側で `量 − trample` を済ませてしまうので、変位も色も**従来の 1 本の経路**がそのまま使える
- 暗くする処理はカバー合成の**後**に置く（trample が量を超えて下地が露出した所も轍として暗くする）
- `uv1.y` は `albedo_occ.a = 1 - uv1.y` として書かれる。occlusion は
  アンビエント・DDGI・疑似バウンスにだけ掛かり**直接光には効かない**ので、
  「日向では輪郭がくっきり／日陰では溝だけが沈む」という見え方になる
- カバーを持たない地形では uv1 が `[0,0]`・法線も摂動なしなので、
  **轍の導入前とビット単位で同じ**出力（回帰テスト `empty_cover_leaves_vertices_bit_identical`）
- GPU の素材 uniform は 1 バイトも変えていない（素材係数は CPU 側で畳んでから頂点へ載せる）

**`uv0.y` は「補間安全な素材添字」でなければならない（黒落ちバグの修正）**

素材添字は頂点属性なのでラスタライザが**線形補間**する。量が 0 へ落ちる帯
（消しゴムの縁・塗りの縁）で添字まで一緒に別の値へ動くと、その中間値が
**塗っていない素材**として `round()` で解決される。たとえば添字 3（泥）の領域を
消すと、縁で添字 2（濡れ＝ほぼ黒）が選ばれ、量に比例して地表が黒く沈む。

そこで頂点へ焼く添字は `CoverSample::blend_material` を使う。これは
**実効量が 0 の点でも、そのテクセルが記憶している素材添字**を返す
（消しゴムは量と轍だけを削り、素材添字は消さない。§3.3）。
結果、消した領域と残っている領域で添字が同じ値に揃い、補間しても常に同じ素材が選ばれる。
量（`uv0.x`）は従来どおり滑らかに 0 へ落ちるので、見た目は滑らかなまま黒縁だけが消える。

- 回帰テスト: `cover_erase_keeps_single_material_index_across_falloff`
- シェーダ側の防御: 解決した添字が有効素材数の外なら**カバー処理を丸ごとスキップ**する
  （`min()` で範囲へ押し込めない。押し込めると壊れた属性が「最後の素材の色」として混ざる）

#### 3.5.9 見栄えの 3 本柱（法線・縁・キャビティ）

**「跡は付くが地味」の確定原因は法線だった。** 変位は CPU が頂点位置へ焼くが、
**法線は焼き直していなかった**ため、凹んだ所も周りも同じ向きを向いたままで
陰影がまったく変わらず、輪郭の位置ズレでしか痕が見えていなかった。
以下の 3 つを足して、参考画像（PSO2 NGS の雪の足跡）のような
「はっきり凹み、陰影が濃く、縁がふっくら盛れる」へ寄せてある。

**① 法線をカバーの高さ場の勾配で摂動する（効果最大・必須）**

```
h(x,z) = 実効の量 × 素材の displacement      … 頂点位置へ焼いているのと同じ式
g      = (∂h/∂x, 0, ∂h/∂z)                   … 中心差分（前後 半テクセル = 0.25m）
n'     = normalize(N − (g − N(N·g)))         … 勾配の接平面成分を法線から引く
```

- 面法線を三角形から積み直す方式は**採らなかった**。チャンク単位でしか三角形を持てないため、
  境界の複製頂点が隣チャンクの三角形を数えられず、**両側で違う法線**になって
  境界に照明の筋が出る。高さ場の勾配なら `CoverNeighborhood` 越しにチャンクを跨いで読めるので、
  §2.6 が位置について保証しているのと同じ理屈で法線まで一致する
  （回帰テスト `boundary_gradient_samples_are_bit_identical_between_neighbours`）
- そのため勾配用の読みは**クランプしない** `CoverNeighborhood::sample_extended` を使う。
  クランプすると境界の頂点だけ片側差分になって隣と食い違う
- 押し出す向きと摂動の入力は**どちらも「カバー適用前の法線」**でなければならない。
  現在の法線を入力にすると適用のたびに摂動が積み重なって法線が倒れ続ける。
  そのため `CoverBaseMesh` は位置と並んで**基準法線**もキャッシュする
- ずらし幅は半テクセル（`0.5 / 32` チャンク UV = 0.25m）。中心差分の幅がちょうど 1 テクセルとなり、
  バイリニア補間で復元できる最小の起伏をそのまま拾う。2 の冪なので境界で丸め誤差も出ない
- 回帰テスト: `cover_height_step_tilts_vertex_normals`

**② 縁の盛り上がり（リム）**

踏み込んだぶんの素材が痕の**外周へ押しのけられて盛れる**。

```
リムの帯 = footprint(形状を 1.4 倍) − footprint(等倍)   … 痕の輪郭を囲むリング
量への加算 = リムの帯 × 強さ × footprint_persistence × 素材の rim_ratio
```

- 加算先は踏み固めチャネルではなく**量チャネル**。こうすると変位・色・法線のすべてが
  既存の 1 本の経路をそのまま通り、描画側に新しい分岐が 1 つも要らない
- 形状を倍率で拡大した差を取るので、**円でもタイヤのトレッド痕でも同じ 1 行**で縁が作れる
- 足す素材は必ず「そのテクセルに今ある素材」なので、`deposit` の異素材置き換え規則
  （削ってから積む）には決して入らない＝踏むたびに縁が確実に高くなる
- 上限は量 1.0。同じ場所を歩き続けると縁はそこで飽和する（＝無限に伸びない）
- チャンク選別（`is_outside_aabb` / `reach_xz`）も 1.4 倍で広げてある。
  等倍のままだと縁だけが載るチャンクが選別で落ちて盛り上がりが切れる
- 回帰テスト: `rim_raises_amount_around_footprint` /
  `rim_is_absent_when_material_has_no_rim_ratio`

**③ 溝のキャビティ（環境光遮蔽）**

`trample_darkening` がアルベドそのものを暗くする（＝直射日光の下でも暗い）のに対し、
`trample_cavity` は G-Buffer の occlusion へ書かれ、アンビエント・DDGI にだけ効く。
溝の底が暗く見える主因は「空が見えなくなること」であり、素材の変色とは別物なので分けてある。
参考画像で溝の中が青みがかって暗いのは、空の色のアンビエントが遮られている状態そのもの。

**採らなかった案: フラグメント側での法線摂動**

「頂点解像度 0.5m ではディテールが足りないので、フラグメントで trample の勾配から
法線を摂動する」案は**見送った**。理由は、情報の上限がカバー場の 0.5m テクセルであって
シェーディング段ではないため。フラグメントが持っているのは頂点から補間された値だけなので、
補間より細かい起伏はそこに存在しない。本当に細かくするならカバー場をチャンクごとの
テクスチャとして GPU へ渡すことになるが、それは §2.3 の
「チャンクごとのバインドグループもテクスチャも増やさない」という設計の柱を崩す
（`max_bind_groups = 5`）。①〜③ で参考画像の見え方には十分届いており、
これ以上を求める段階になったら、カバー場の解像度そのもの（§2.1）を上げるほうが筋が良い。

#### 3.5.7 Play 揮発とスコープ

- 轍は**積算とまったく同じ扱い**で、Play 中に積み、Stop で捨てられる（`cover_play_snapshot`）
- **Edit での轍オーサリングはスコープ外**。「どこを歩いたか」は Play でしか生まれない情報であり、
  シミュレートボタン（Edit）では轍は動かない
- 進行方向・前フレーム位置の追跡（`cover_stamp_tracks`）は Play の開始と終了で必ず捨てる

#### 3.5.8 性能

- スタンプは **移動時のみ**（前フレームから 0.001m 未満しか動いていないソースは完全に無視）
- 触るチャンクは**スタンプの AABB に交差するものだけ**（既定 48 チャンクのうち 1〜4 個）。
  Y も「接地点 ± 許容差」で判定するので、別の段のチャンクには一切触れない
- 変化したチャンクだけを既存の `queue_cover_apply` 経路へ載せる
  ＝ 頂点の焼き直しも接地点の周りに閉じ、間引き（`COVER_APPLY_INTERVAL_SEC`）もそのまま効く
- 計測: `SEED_PERF_LOG=1` で `[PERF terrain] cover stamp sources=N chunks=M (X.XXms)`

## 4. エミッタ（`CoverEmitterComponent`）

アクターに付けるだけで、そのアクターの位置を中心に素材が降る。
**中心位置はアクターの `Transform` から解決される**（コンポーネントは位置を持たない）
＝ギズモで動かすとそのまま降る場所が動く。`WaterVolumeComponent` の Region と同じ規約。

| フィールド | 既定 | 意味 |
|---|---|---|
| `range_kind` | `Region` | `Global` / `Region` / `TextureMask` |
| `extents` | `[8,8,8]` | Region の各軸半径（m） |
| `fade` | `1.0` | Region の境界フェード幅（m）。0 で硬い境界 |
| `mask_path` | `""` | TextureMask のグレースケール画像。空 = このエミッタは無効 |
| `mask_size` | `[32,32]` | TextureMask の XZ サイズ（m） |
| `material_id` | `"snow"` | cover_materials.json の `id` |
| `strength` | `0.2` | 量/秒（0.2 = 5 秒で満量） |
| `enabled` | `true` | データ側の有効フラグ（スロットの有効/無効とは別） |

> **既定が `Global` でない理由**: 追加した瞬間にワールド全域が雪で埋まる
> （取り返しの付きにくい編集が 1 フレームで起きる）事故を避けるため。

- マスク画像は **R チャンネル**をそのまま被覆率として読む（白 = 強度そのまま、黒 = 降らない）。
  矩形の外は 0。読み込み失敗は「無効なマスク」としてキャッシュし、毎フレームの再読み込みを避ける
- 未定義の `material_id`・強度 0・無効マスクのエミッタは、積算ループに入る前に落とされる
- インスペクタは範囲種別に応じて無関係な項目を非表示にする（既存方針どおり）

## 5. 編集フロー（Edit）と Play

### Edit — インスペクタの「シミュレート（編集）」セクション

操作は **3 つに分かれている**。「秒数を空にすると意味が変わる」といった兼用は無い。

| 操作 | 挙動 | Undo 単位 |
|---|---|---|
| **▶ / ■**（再生/停止トグル） | リアルタイムに毎フレーム積算し続ける。もう一度押すと止まる。**秒数欄の値は読まない** | 再生〜停止の 1 セッションで **1 コマンド** |
| **N 秒進める** | 隣の秒数欄の値ぶんを**即座に**計算して停止する。欄が空・0 以下ならボタンは無効（disabled） | 1 押し = **1 コマンド** |
| **全消去** | 全チャンクのカバー場を消す | **1 コマンド** |

トグルの見た目（▶ / ■）は、押した瞬間ではなく**ランタイムからの通知**
（`TERRAIN_COVER_SIM_STARTED` / `TERRAIN_COVER_SIM_STOPPED`）で切り替わる。
全消去や Play 開始でランタイム側が勝手に停止したときも通知が飛ぶので、
ボタンが「再生中のまま取り残される」ことが無い。

再生中に「N 秒進める」を押した場合、その分は**停止時の 1 コマンドへ畳み込まれる**
（再生セッションの途中に別の Undo 単位を割り込ませない）。

結果は編集データとしてカバー場に書かれ、`.tcover` として保存される。保存の起点は 2 つある。

| 起点 | 書く範囲 | 通知 |
|---|---|---|
| 「地形を保存」ボタン（`TERRAIN_SAVE`） | **全チャンク**（ロード時の確実な復元が目的） | `TERRAIN_SAVE_OK:{count}` |
| **シーン保存（Ctrl+S / `SAVE_SCENE`）** | **ダーティなチャンクだけ** | なし（`SAVE_OK` に含める。失敗時のみ `TERRAIN_SAVE_ERROR`） |

シーン保存に相乗りするのは、地形の実体（`.tvox` / `.tscatter` / `.tcover`）が `.scene` の外に
住んでいるためである。雪を積もらせた直後に Ctrl+S だけしてエディタを閉じると作業が丸ごと消える、
という取り返しのつかない失われ方をしていた。「保存」と言われたら地形も保存されるのが唯一素直な挙動である。

ダーティ集合が空なら**ディレクトリ作成すら行わず即座に帰る**ので、
地形を一切触っていないセッションで Ctrl+S が遅くなることはない
（`App::flush_dirty_terrain`。`handle_terrain_save` とは書く範囲だけが違う別関数）。

> **Play 中の Ctrl+S はカバー場を書かない。** Play 中の積算・轍は揮発が仕様（Stop で
> Edit の保存状態へ戻る）なので、ここで焼くと「消えるはずの雪が永久に残る」。
> 判定は `cover_play_snapshot` が生きているか。`cover_dirty` は消さずに残すため、
> Stop したあとの保存でちゃんと書かれる。
> （「地形を保存」ボタンは従来どおり無条件に全部書く。こちらは明示操作なので変えていない。）

秒数指定は 60Hz 相当で刻むが、ステップ数は `COVER_SIMULATE_MAX_STEPS`（600）で頭打ちにし、
超える場合は刻み幅のほうを伸ばす。自然減衰が無く積算が単調加算なので、
**刻み幅を変えても飽和前の合計量は厳密に同じ**である（エディタが固まらないための安全弁）。

### Edit — 地形編集モードの「カバー」ブラシ（手編集）

エミッタで降らせるのとは別に、**地形編集モードのツールバーからブラシで直接編集できる**。
「積もらせたあと一部だけ消す」「エミッタのシミュレートを待たずに手で雪を敷く」ための道具である。

| ツール | モード | 効果 |
|---|---|---|
| **カバー** ＋ 「消去」ON（既定） | 消しゴム | ブラシ範囲の**量と踏み固め（轍）**を強さに応じて減らす。消え切ったテクセルは素材も空へ戻る |
| **カバー** ＋ 「消去」OFF | 塗り | ブラシ範囲を、選択した素材の**目標量**へ近づける |

パラメータは既存のブラシ群と共通の流儀にしてある。

| パラメータ | 意味 | 備考 |
|---|---|---|
| 半径 | ブラシ球の半径（m） | 密度ブラシと共通のスライダー・Ctrl+ホイールで調整 |
| 強度 | **1 発**で動かせる量（0〜1） | Shift+ホイールで調整。強度 1.0 の中心テクセルで `COVER_BRUSH_MAX_DELTA_PER_APPLY`（0.25） |
| 素材 | 敷く素材（`cover_materials.json` の並び） | 塗りモードのみ表示。消去では読まれない |
| 目標量 | 敷く厚み（0〜1） | 塗りモードのみ表示。なぞった場所はこの量へ**両方向から**収束する |
| ブラシテクスチャ | ブラシの**形状マスク**（グレースケール画像。未指定なら円形） | 地形設定ウィンドウの「ブラシ」タブ。レイヤペイントブラシと**共有**する共通設定（下記） |

着弾点は密度ブラシ・散布ブラシと同じ `terrain_raymarch_hit`（＝プレビュー球と必ず一致する）。

#### ブラシテクスチャ（形状マスク）

半径・強度と同じ**ツール共通のブラシ設定**であり、レイヤペイントブラシ（`TERRAIN_PAINT`）と
カバーブラシ（塗り／消去の両方）で同じ 1 つの値を共有する。正典の仕様は
**docs/terrain.md §9.9**（純粋層は `terrain/brush_mask.rs`）。要点だけ再掲する。

| 項目 | 値 |
|---|---|
| 画像の読み方 | **R チャンネル**のみ（`CoverMask::sample`・最近傍）。白=フル強度 / 黒=0 |
| 貼り付け範囲 | ブラシ球の **XZ バウンディング正方形**（中心 = 着弾点、一辺 = 2 × 半径）。**回転しない** |
| UV 規約 | `u = (world_x - center_x) / (2r) + 0.5` / `v = (world_z - center_z) / (2r) + 0.5` |
| V の向き | 画像の上端が **-Z** 側、左端が **-X** 側（= エミッタの `TextureMask` と同じ向き） |
| 未指定のとき | **従来どおりの円形フォールオフ**（挙動はビット単位で従来と同一。回帰テストで固定） |
| 読み込み失敗のとき | 円形フォールオフへ**縮退**（効果 0 にはしない＝ブラシが黙って無反応にならない） |
| IPC | `TERRAIN_BRUSH_MASK:{path}`（空文字で解除）。ブラシ 1 発ごとのコマンドには載せない |

デコード済み画像はエミッタの `TextureMask`・轍スタンプの `Texture` と**同じキャッシュ**
（`TerrainState::mask_cache`）に載る。同じ画像を 2 用途で二重にデコードしない。

設計上の決めごとは 4 つ。

1. **dt を掛けない。** ブラシは「1 回押すたびに一定量」効く道具である。dt を掛けると
   フレームレートで同じドラッグの結果が変わる（密度ブラシ・レイヤペイントも同じ理由）。
   連続適用の速さはエディタの送信スロットル（40ms）が決める。
2. **Y 照合は上下対称。** 着弾点は必ず面の上（レイマーチ交点）なので、轍スタンプの
   接地スナップ（§3.5.2-b）に相当するものは要らない。窓そのものは必要で、
   これが無いと地表をなぞったブラシが**真下の洞窟の床の雪まで消す**。
   許容差はブラシ半径（下限 `COVER_BRUSH_Y_TOLERANCE_MIN` = 0.5m）。
3. **消去は傾斜を見ない／塗りは見る。** 「積もりにくい斜面」は積もる側の規則であって、
   既にそこにあるカバーを消せない理由にはならない。逆に塗りは積算とまったく同じ
   `slope_scale` を通し、「エミッタで積もる面 ⇔ 手で塗れる面」を一致させる。
4. **塗りは目標量へ両方向から近づける。** 単純加算だと「厚くしすぎたら消しゴムに持ち替える」
   必要が出る。目標量へ収束させると、なぞった場所の厚みがストローク回数に依らず決まる
   （何往復しても同じ絵になる）。異素材の上に塗るときだけは `deposit` と同じ置き換え規則
   （古い素材を削り切ってから新素材が乗る）を通り、エミッタで降らせた場合と手触りが揃う。

境界の一貫性・保存は既存経路をそのまま通る。変化したチャンクは `queue_cover_apply`
（26 近傍を焼き直し待ちへ入れる。§2.6）と `cover_dirty`（Ctrl+S / `TERRAIN_SAVE`）に載る。

### Undo（管轄は「操作した場所」で決める）

#### 管轄の線引き — **操作した場所で戻る**

カバー場の Undo は **2 本の履歴に分かれている**。分ける基準はデータの種類ではなく
**どこで操作したか**である。エディタが `TERRAIN_UNDO` を送るのは地形編集モード中の
Ctrl+Z だけ（`MainWindow.Input.cs` の `_terrainMode ? "TERRAIN_UNDO" : "UNDO"`）なので、
この基準にすると「操作したのと同じ場所で 1 回ずつ戻る」が常に成立する。

| 対象 | 操作した場所 | 履歴 | エディタが送るキー |
|---|---|---|---|
| 地形の**密度・ペイント**（ブラシのストローク） | 地形編集モードのツールバー | terrain 専用スタック（`TerrainEdit` / `TERRAIN_UNDO_MAX = 32`） | 地形編集モード中の Ctrl+Z → `TERRAIN_UNDO` |
| **カバー場（カバーブラシ）**（消しゴム／塗りのストローク） | 地形編集モードのツールバー | terrain 専用スタック（`TerrainEdit.cover_before` / `cover_after`） | 地形編集モード中の Ctrl+Z → `TERRAIN_UNDO` |
| **カバー場（エミッタ操作）**（再生セッション／N 秒進める／全消去） | `CoverEmitterComponent` のインスペクタ | メイン履歴（`CoverFieldEditCommand` / `MAX_HISTORY = 100`） | 通常の Ctrl+Z → `UNDO` |

同じ 1 つの操作が両方の履歴へ載ることは無い（載せると 1 回の操作を 2 回戻せてしまう）。

**カバーブラシ側の区切り方**は密度ブラシと完全に同じ「1 ストローク = 1 Undo 単位」であり、
左ボタン解放で飛ぶ `TERRAIN_STROKE_END` が確定する。ストローク中に触れたチャンクの
「編集前」カバー場は `TerrainState.cover_stroke_before` に集約され、確定時に
**実際に変化したチャンクだけ**が `TerrainEdit` へ載る（ブラシ球は容易に隣のチャンクへ
はみ出すので、触れただけのチャンクを積むと Undo エントリが無駄に太る）。
密度スナップショット（143KB/チャンク）とカバー場（2KB/チャンク）を別マップに分けてあるのは、
雪を消しただけのストロークで密度まで控えるのが純粋な無駄だからである。

**エミッタ側**の Undo は以下のとおり（従来どおりメイン履歴）。

カバーの操作入口は `CoverEmitterComponent` の**インスペクタ**であり、ユーザーから見れば
コンポーネント操作の一部である。ところがエディタは**地形編集モード中にしか `TERRAIN_UNDO` を送らない**
（`MainWindow.Input.cs` の `_terrainMode ? "TERRAIN_UNDO" : "UNDO"`）。
そのため地形専用スタックへ積むと「コンポーネント追加 → シミュレート → Ctrl+Z」で
**雪は残ったままコンポーネント追加のほうが取り消される**という壊れた順序になる（実際に発生した不具合）。
メイン履歴へ積むことで、この順序は「1 回目 = 雪が戻る／2 回目 = コンポーネント追加が戻る」に一本化される
（回帰テスト: `undo.rs::cover_edit_undoes_before_earlier_component_add`）。

逆に、**地形編集モード中の Ctrl+Z（`TERRAIN_UNDO`）はエミッタ操作のぶんを戻さない**
（戻すのはカバーブラシのストロークだけ）。両方の履歴に載せると 1 回の操作を
2 回戻せてしまうため、1 つの操作の巻き戻し口は必ず 1 本に限る。

#### コマンド

```rust
pub struct CoverFieldEditCommand {
    pub before: HashMap<ChunkCoord, CoverField>, // 変化したチャンクのみ
    pub after:  HashMap<ChunkCoord, CoverField>, // before と同じキー集合
}
```

`execute` / `undo` は **No-op** である。カバー場の実体は `App.terrain`（Scene の外）にあり、
書き戻しには再焼き付け予約や `.tcover` のダーティ化も伴うため、`SlotFieldEditCommand` と同じく
**AppBase が `cover_fields_for_undo/redo()` を peek して `restore_cover_snapshots` で適用する**
（`ipc_handler.rs` の `IpcCommand::Undo` / `Redo` の腕）。

密度スナップショットと同居させない理由もここにある。1 チャンクの密度は 33³×4B ≒ 143KB あるのに対し
カバー場は 2KB しかなく、雪を積もらせただけで密度を控えるのは純粋な無駄である。

セッションの取り方（`terrain_cover_ops.rs`）:

| 関数 | 役割 |
|---|---|
| `begin_cover_undo_session` | 開始時に `terrain.cover` を丸ごと複製（48 チャンクで約 96KB）。**既にセッション中なら何もしない**（多重開始で before を壊さない） |
| `commit_cover_undo_session` | before と現在の**和集合**を走査し、`CoverField` が実際に変わったチャンクだけを before/after へ入れて `undo_history` へ 1 コマンド record。差分ゼロなら**何も積まない**（空コマンドで履歴を汚さない） |
| `stop_cover_sim_and_commit` | 連続シミュレートを止めて確定する（全消去・Play 開始からも呼ばれる） |

「そのチャンクにカバー場が無かった」状態は `CoverField::new()`（全ゼロ）で表現する。
空フィールドは保存時に `.tcover` ごと削除される規約（§3.4）なので、存在しないのと等価である。

undo/redo の適用（`restore_cover_snapshots`）は、書き戻し・`cover_dirty`（`.tcover` 保存の dirty 化）・
`cover_pending_apply`（頂点への再焼き付け予約）の 3 点をまとめて行い、`cover_apply_timer` を満了させて
次フレームで即座に焼き直す。**カバーのみのエントリでは `remesh_chunks` は呼ばない**
（密度は変わっていないので再メッシュは無駄なうえ、カバーの派生キャッシュを捨ててしまう）。
密度側の undo と同じく、**現存しないチャンクは書き戻さない**（ハイトマップ再読込等でチャンク集合が
作り直された場合に幽霊チャンクの `.tcover` が復活するのを防ぐ）。

**メモリ**: 1 コマンド = 4KB × 変化チャンク数（before + after）。既定 48 チャンクが全変化して約 192KB。
メイン履歴の上限 `MAX_HISTORY = 100` を**すべて**カバー編集で埋めた最悪ケースで約 19MB
（現実には他の操作と混ざるので届かない）。密度 1 ストローク（143KB×2×チャンク数）より 1 チャンクあたり 35 倍軽い。

### Play — 積算は揮発する

Play 中は有効なエミッタが毎フレーム積算する。**Play 中に積もったぶんは Stop で捨てられ、
Edit の保存状態へ戻る**（水位 `sim_level_y` とまったく同じ考え方）。
Play 開始時にカバー場を丸ごと複製し、終了時に書き戻している（1 チャンク 2KB なので複製は無視できる）。
Play しただけでシーンが「変更済み」にはならない。

### シーンギズモ

`CoverEmitterComponent` を持つアクタを選択すると、降る範囲がシーンビューへワイヤ描画される
（`cover_emitter_scene_gizmo.rs`。camera / light / skybox などのギズモと同型）。

| `range_kind` | 描くもの |
|---|---|
| `Global` | **何も描かない**（無限範囲。線が出ないこと自体が Global の表示） |
| `Region` | `extents` の直方体ワイヤ（外枠）＋ `extents - fade` の薄い内枠（境界フェード幅の二重枠） |
| `TextureMask` | `mask_size × 0.5` を半径とする XZ 水平矩形枠＋四隅の縦目印線（マスク画像の内容は描かない） |

**ギズモは軸平行で描く**。積算側（`collect_cover_emitters`）がアクタの位置しか使わず、
回転もスケールも範囲へ適用していないため。回転を反映させると「ギズモは傾いているのに
実際は傾かずに降る」という嘘のギズモになる。

`enabled` が false のエミッタ、および `mask_path` が空の `TextureMask`（＝実際に降らない）は描かない。

#### `InteractionSourceComponent` のギズモ（I3.2）

`InteractionSource` を持つアクタを選択すると、影響範囲と**作用状況**が描かれる
（`interaction_source_scene_gizmo.rs`）。

| 描くもの | 意味 |
|---|---|
| 影響半径のワイヤ球（水平リング＋縦リング 2 枚） | 草・水面へ書き込む範囲。`Circle` 形状なら痕の広がりそのもの |
| 真下へ伸びる線＋上下端の十字 | **接地スナップの Y 窓**（3.5.2-b）。上端 = `y_tolerance`、下端 = `ground_reach_down` |
| 回転した矩形＋進行方向の矢 | `Texture` 形状のスタンプ矩形（`stamp_size`）。向きは追跡中の進行方向、未追跡なら +Z |

**色で作用状況を示す**（切り分け用。状態は Play 中のみ更新される）。

| 色 | 意味 |
|---|---|
| 緑 | 通常（静止している／Play していない） |
| シアン | 移動中 ＝ インタラクションフィールド（草・波紋）へ書き込んでいる |
| オレンジ | **今まさに轍を押した**（カバー場が実際に変化したフレーム。0.25 秒保持） |

この 3 色があると「轍が付かない」ときの切り分けが目視でできる。
- 緑のまま動かない → 収集で落ちている（active / slot enabled / 半径・強さ 0 / Play していない）
- シアンにはなるがオレンジにならない → 収集は通っている。Y 窓が地面に届いていないか、
  そのテクセルにカバー（雪）が無いか、素材の `footprint_persistence` が 0
- **Y 窓の下端の十字が地面より上に浮いていたら、その時点で絶対に痕は付かない**

寸法は `CoverStampSpec` のメソッド（`y_tolerance` / `ground_reach_down`）から直接引いており、
実装を変えればギズモも自動で追従する（値を書き写していない）。
`enabled` が false・半径 0・強さ 0 のソース（＝実際に何も起きない）は描かない。

### パフォーマンス計測

- `SEED_PERF_LOG=1` → 毎フレームの `[PERF f=...] ... cover=<ms>` に積算＋焼き直しの CPU 時間が出る
- 同フラグで `[PERF terrain] cover apply chunks=N total=<ms>`（焼き直しの内訳）も出る
- 頂点の焼き直しは `COVER_APPLY_INTERVAL_SEC`（0.1 秒）で間引く。
  積算そのものは毎フレーム進むので、雪の量が飛ぶことはない

## 7. 既知の制限（I3.2 時点）

1. **同一チャンク内の上下 2 面は区別できない（XZ 投影）**。
   カバー場はチャンク（3 次元インデックス）紐づけなので、地表と洞窟の床は多くの場合
   そもそも別チャンクになり別々のカバー場を持つ。同一チャンク内に上下 2 枚の面がある場合のみ、
   **上の面が勝つ**（積算そのものの制限）。
   I3.2 の Y 照合は「**どのチャンクの面を読むか**」を解決するもので、
   1 チャンク内に 2 枚ある場合の分離ではない（分離には多層化が要る）。
2. ~~**RT（レイトレ）は変位前の地形を見る**~~ → **修正済み（毎フレーム追従する）**。
   かつてはカバーの焼き直しが BLAS を作り直さず、RT が「古い高さの地形」を辿っていた。
   フレームの実行順は「カバー焼き込み（更新）→ BLAS 構築（描画）」なので、
   **カバーの載ったシーンをロードすると BLAS は「積もった高さ」で作られる**。
   その状態で消しゴムを掛けるとラスタの地表だけが素の高さ（既定の雪で 22cm 下）へ戻り、
   RT 影のレイ原点が「まだ在ることになっている雪」の内側へ沈む。レイ原点のバイアスは
   2.5cm しかないため、**なぞった領域が全面遮蔽＝真っ黒になる**
   （密度ブラシで穴を掘ったときの黒落ちとまったく同じ機構）。

   現在は頂点が動いたチャンクを `TerrainState::rt_blas_prune_pending` へ溜め、
   **毎フレーム**（`frame_renderer` のカバー焼き直し直後）
   `terrain_ops.rs::flush_rt_blas_prune` が `prune_rt_blas_caches(keys)` で
   その BLAS だけを捨てる（**統合バッチは捨てない**。§2.8）。
   次フレームに最新頂点で BLAS/TLAS が組み直され
   RT 影・RT 反射・RT AO が追従する。**ストローク中かどうかで分岐しない**ので、
   なぞっている最中も黒が出ない。

   同じ集合には**密度ブラシのストローク中再メッシュ**（`remesh_chunks(defer_side_effects=true)`）も
   積む。どちらも「ラスタの地表が動いたのに BLAS が古い形のまま残る」まったく同じ不整合であり、
   掘る操作の黒落ちも同じ経路で解消される。

   **消化には件数予算がある**。1 フレームに捨ててよいのは
   `rt_shadow::MAX_BLAS_BUILDS_PER_FRAME`（= 8）チャンクまでで、これは BLAS の
   1 フレーム再構築上限と同じ値である（超えて捨てても再構築が追いつかず、影が抜けている
   時間が伸びるだけ。単一情報源としてユニットテスト
   `rt_prune_budget_matches_blas_build_limit` で一致を固定）。
   捨ててからまだ作り直されていないチャンクは `prepare_and_build` の TLAS 詰め直しで
   `blas_cache.get()==None` として素通りされるため、**古い形で誤遮蔽するのではなく
   一時的に影を落とさない**という安全側へ縮退する（数フレーム影が薄いだけで黒くはならない）。

   > **旧実装の不具合（回帰テスト `rt_blas_prune_is_flushed_from_frame_loop_only` で固定）**
   > 消化処理を `apply_pending_cover` の**内側**から呼んでいた。あのメソッドは
   > 「焼き直し待ちが空なら先頭で return」するため、マウスを離した時点で待ちが空だと
   > 消化が二度と発火せず、黒が残り続けた。待ちが残っていたときだけ偶然直るので
   > 「たまに消した後に解消することもあるが絶対ではない」という症状になっていた。
   > 消化は毎フレーム無条件に走る場所から呼ぶこと。

   なお RT 影マスクのデノイズ（`shadow_mask.rs`）は `mask_raw` を毎フレーム生成し直すので、
   黒が**構造として**引きずられることはない。ただし Phase RT-Shadow-Denoise 追補で
   **テンポラル EMA**（α=`SHADOW_MASK_EMA_ALPHA`=0.25、カメラ静止時のみ有効）が入ったため、
   カメラを止めたままストロークすると影マスクの値が数フレーム（時定数 ~4 フレーム＝60fps で ~67ms）
   遅れて追従する。深度が変わらない変更（カバー素材の差し替えなど）では EMA の画素単位棄却
   （深度相対差）が効かないためこの遅延は残るが、必ず数フレームで収束するので
   「黒が残り続ける」類の不具合にはならない。ストローク中に履歴をリセットする仕組みは不要である。
3. **物理コライダーは変位を反映しない**。コライダーは密度場から別途生成される。
   数センチの積雪の上を歩く／沈むといった挙動は本フェーズの担当外。
4. **法線は変位で作り直さない**。変位が小さい前提の近似。
5. **異なるカバー素材どうしの境界は硬いエッジ**。素材添字は頂点間で補間できないため
   フラグメント側で `round()` する。頂点へ載せる素材は「**バイリニア重み × 量が最大のテクセル**」
   から採る（実質的に最近傍だが、**量 0 のテクセルは決して選ばない**）。
   量のほうは滑らかに補間されるので実画像では目立たない。
   なお「カバー ⇔ カバー無し」の境界は添字が動かない（`blend_material`。§3.5.6）ので
   この制限に当たらない。**2 種類のカバー素材が直接隣り合う場合のみ**、
   その 1 三角形ぶんの帯で中間の添字が解決されうる（多層化まで残る既知の制限）。
6. **Undo はメイン履歴（通常の Ctrl+Z）の管轄で、地形密度の Undo とは別スタック**。
   シーンビューにフォーカスがある状態の Ctrl+Z が `UNDO` として届く
   （インスペクタ入力中の Ctrl+Z はテキストボックスの undo になる）。
   **地形編集モード中の Ctrl+Z は `TERRAIN_UNDO` になり、カバー場は戻らない**（§5 の管轄表）。
   カバーを戻したいときは地形編集モードを抜けてから Ctrl+Z する。
   Play 中の揮発積算は Undo 対象外（Stop で保存状態へ戻るので、そもそも戻すものが無い）。
7. **1 チャンクに 1 層**。多層（雪の下に落ち葉が残る）は将来判断。
8. ~~**上下（Y）のチャンク境界には段差が残りうる**~~ → **I3.2 で解消**（§3.5.2）。
   テクセルごとの基準 Y をワールド位置の純関数として解き、
   境界面上の複製頂点が上下段どちらから読んでも同じ面を選ぶようにした。
   回帰テスト `y_boundary_sample_is_bit_identical_between_stacked_chunks` が固定する。
9. **轍は物理・コライダー・RT に反映されない**（制限 2・3 と同じ理由）。
   踏み固めで雪が消えた所も、コライダーは元の地形のままである。
10. **轍の解像度はカバー場と同じ 0.5m 刻み**。それより細かい靴底の模様は
   テクスチャ形状を使ってもテクセルに丸められる（足跡 1 個は数テクセルの窪みとして出る）。
11. **世界の端ではカバーが半テクセルぶんなだらかに 0 へ落ちる**（隣接チャンクが無い側は
   量 0 として読むため。§2.6）。既定 0.5m 刻みなので 0.25m 幅であり、実用上は見えない。

## 9. 実機での確認手順（谷に雪を積もらせる）

1. エディタで地形を作る（地形メニュー → 初期化）。ブラシで **谷と斜面**を彫る
   （傾斜ルールの効きを見るため、急斜面と平地の両方を作ること）
2. 任意のアクターを選び、インスペクタの「コンポーネント追加」→ 環境 → **Cover Emitter**
3. アクターを谷の上へ移動する（ギズモ）。範囲は既定の `Region`（半径 8m 立方）のまま
   - → **シーンビューに水色の直方体ワイヤが出る**。`fade` を 0 → 2 と動かすと内側の薄い枠が縮む
   - アクタを動かすとワイヤも追従する。**アクタを回転させてもワイヤは傾かない**（仕様。実際の範囲が軸平行なため）
   - 範囲を `Global` にするとワイヤが消え、`TextureMask` にすると XZ の紫の矩形枠になる
     （`mask_size` を 32→64 にすると枠が 2 倍になることを確認）
4. 素材 ID は既定の `snow`、強度は既定の `0.2`
5. 「シミュレート（編集）」の秒数欄 **`5`** のまま **`5 秒進める`** を押す
   - → 谷の平らな面が白く盛り上がる。**急斜面には積もらない**ことを確認する
   - 秒数欄を空にするとボタンが**押せなくなる**（disabled）ことを確認する
6. **▶** を押すと積もり続け、ボタンが **■** に変わる。もう一度押すと止まり ▶ に戻る
7. 範囲を **Global** に変えて 5 秒進めると、地形全体の緩斜面が雪で覆われる
8. 素材 ID を `wet` に変えて 5 秒進めると、雪が削られてから濡れた黒い地面へ変わる
   （置き換え規則の確認）
9. **Undo の確認**（**地形編集モードを抜けてから**シーンビューをクリックしてフォーカスを移し **Ctrl+Z**）
   - 「5 秒進める」1 押しぶんが 1 回の Ctrl+Z で丸ごと戻る（複数回に分かれない）
   - ▶ で 10 秒ほど積もらせて ■ で停止 → Ctrl+Z 1 回で**再生前の状態まで**戻る
   - **全消去** → Ctrl+Z で雪が戻る。もう一度 Ctrl+Y（redo）で再び消える
   - **積み順の確認（本節の要）**: 新しいアクタに Cover Emitter を**追加**してから 5 秒進め、
     Ctrl+Z を 2 回押す。**1 回目で雪が戻り、2 回目でコンポーネント追加が取り消される**こと
     （逆順になっていたら回帰）
   - 地形編集モード中の Ctrl+Z（`TERRAIN_UNDO`）では**雪は戻らない**（仕様。§5 の管轄表）。
     この状態ではブラシで彫った地形だけが戻る
10. 地形メニューから **保存**。シーンを開き直しても雪が残っていることを確認する
11. **Play** → 雪がさらに積もる。**Stop** → 保存した状態へ戻る（Play 中の積算は揮発）
    - ▶ で再生したまま Play へ入ると、ボタンが自動で ■ → ▶ に戻る（再生はランタイム側で締められる）

## 10. 実機での確認手順（雪原を歩いて轍を残す・I3.2）

1. §9 の手順で雪原を作る（`Global` の Cover Emitter ＋ `5 秒進める` で地形全体を白くする）
2. 動かすアクタ（キャラクターでも Cube でもよい）を選び、
   「コンポーネント追加」→ **Interaction Source** を追加する
   - 「轍（地表カバーへの痕）」セクションが出る。形状は既定の **円 (Circle)**
   - 影響半径は既定 1m のまま
   - **選択した時点で緑のワイヤ球と、真下へ伸びる Y 窓の線が出る**。
     Y 窓の下端の十字が雪面より下にあることを確認する（浮いていると痕は付かない）
3. **Play** して、そのアクタを雪原の上で動かす（スクリプト・物理・ギズモのいずれでもよい）
   - → 通った跡が**筋状に凹み、わずかに暗くなる**
   - → 同時にギズモが**シアン（移動中）→ オレンジ（轍を押した）**へ変わる
   - 立ち止まっている間は何も起きない（移動時のみスタンプ）／ギズモは緑へ戻る
   - **アクタの原点が地面より高くても轍は付く**（接地スナップ。3.5.2-b）。
     床から 2m 以上浮かせると付かなくなり、Y 窓の下端が地面から離れるのが見える
4. **降雪で埋まることの確認**: Cover Emitter の強度を 0.2 のままにして Play を続ける
   - → 古い轍から順に浅くなり、やがて消える。エミッタを無効にすると轍はそのまま残り続ける
5. **Stop** すると轍は消え、Edit の保存状態（轍のない雪原）へ戻る（Play 揮発）
6. **テクスチャ形状の確認**（任意）
   - 黒背景に白い模様を描いた PNG を用意する（例: 縦に伸びるトレッド模様 256×256）
   - 形状を **テクスチャ (Texture)** に変えると「痕画像」「痕の幅X」「痕の長さZ」の 3 行が出る
     （円のときは非表示）。画像をドラッグ&ドロップするか参照ボタンで指定する
   - Play して動かすと、模様が**進行方向を向いて**押される。向きを変えると痕も追従する
7. **Y 照合の確認（洞窟）**: ブラシで地表の下に洞窟を掘り、洞窟の床にも雪を積もらせる
   - 洞窟の床を歩いても、**頭上の地表には轍が付かない**こと
8. **Y 境界の段差が消えたことの確認**（I3.1 §7-8 の回帰）
   - 地表がちょうど Y=16m（既定チャンク境界）付近を水平に通る地形を作り、雪を積もらせる
   - その等高線に沿って**筋状の段差が出ない**こと（カメラを寄せて斜めから見る）
9. **素材差の確認**: エミッタの素材 ID を `wet` にして 5 秒進める（雪が濡れへ置き換わる）
   - → 濡れた地面を歩いても**痕が一切残らない**（`footprint_persistence` が 0）

## 11. 実機での確認手順（カバーブラシで雪を消す・敷く）

1. §9 の手順で雪原を作る（エミッタで 5 秒ぶん積もらせておく）
2. シーン編集モードを **terrain** にし、ツールバーで **カバー** を選ぶ
   - 「消去」が既定 ON。素材／目標量の欄は消去中は出ない（塗りに切り替えると現れる）
3. **消しゴムの確認**: 半径 3m・強度 0.5 のままシーンビューを左ドラッグする
   - → なぞった場所の雪が**その場で消えて**地面が出る（縁は滑らかに落ちる）
   - → 轍が付いていた場所は轍ごと消える（量だけ残った窪みにならない）
   - ブラシの当たる範囲は既存の**プレビュー球**でそのまま見える（密度ブラシと同じ）
4. **Undo の確認**: 左ボタンを離してから Ctrl+Z
   - → **1 ストロークぶんがまとめて**戻り、消した雪が復活する
   - もう一度 Ctrl+Z すると、その前に行った地形編集（掘る等）が戻る
     （＝地形編集モードで行った操作が、操作した順に 1 本で戻る）
   - Ctrl+Shift+Z で redo すると、また消えた状態へ進む
5. **塗りの確認**: 「消去」を OFF にし、素材＝雪・目標量＝1.00 でドラッグ
   - → エミッタのシミュレートを待たずに、なぞった場所へ雪が敷かれる
   - 目標量を 0.3 にして同じ場所をなぞると、**厚みが 0.3 まで下がって止まる**
     （何往復しても厚みが変わらない＝目標量へ収束している）
6. **素材置き換えの確認**: 素材を `mud` に変えて雪の上をなぞる
   - → まず雪が削れ、消え切ってから泥が乗り始める（エミッタで降らせた場合と同じ手触り）
7. **Y 照合の確認（洞窟）**: 地表の下に洞窟を掘り、洞窟の床にも雪を積もらせる
   - → 地表を消しゴムでなぞっても、**真下の洞窟の雪は消えない**
8. **チャンク境界の確認**: チャンク境界をまたぐようにブラシをドラッグする
   - → 境界に**隙間も段差も出ない**（変化チャンクの 26 近傍が焼き直されるため）
9. **保存の確認**: Ctrl+S でシーンを保存し、シーンを開き直す
   - → 消した／敷いた結果がそのまま復元される
   - チャンクの雪を全部消してから保存すると、そのチャンクの `.tcover` が**削除**される
     （`runtime/assets/terrain/<scene>/` を確認。消したはずの雪が復活しない）
